# API — контракт между клиентом и движком

✅ **Состояние: построен на первом экране (17.09).** Охрана — `core/api.py`
(`api_guard`, `api_require`, `api_body`), конверт — `core/layout.msg_json`,
первые маршруты — `GET`/`POST /api/settings/clinic` в
`modules/settings/api.py`. Старые JSON-адреса (`/slots`, `/doc/{id}/open`,
`/theme/palette`) не трогались: у них свои формы ответа, и их клиенты —
серверные страницы.

Правила, которые держит `test_structure`: маршрут под `/api/` зовёт
`api_guard`/`api_require` и никогда `_guard`/`require`; адрес пишется
полным путём в декораторе (без `prefix` у роутера) — карта экранов и сторож
читают его оттуда.

## Конверт

```json
{ "ok": true, "code": "ok_set", "tone": "ok", "text": "Setări salvate",
  "field": "name", "data": {} }
```

`text` и `tone` — перевод кода, сделанный на сервере (`msg_json`): клиент
показывает `text` и красит по `tone`, а кодов не переводит. Код вне словаря
уезжает с пустым текстом, и клиент показывает свою единственную фразу «движок
не отвечает». `field` — только при 422.

⛔ `code` — существующий код из `core/layout.MSG_BANNER` (90 штук), **не новая
строка**. Тексты живут на сервере; второго словаря в TypeScript быть не должно.

## Коды ответа

| | Когда |
|---|---|
| `200` | получилось |
| `401` | не вошёл или сессия истекла |
| `403` | вошёл, но роль не пускает (`PERMS`) |
| `409` | конфликт: занятый слот, дубль пациента, запись уехала |
| `422` | не прошла проверка; `field` называет поле формы |

Разбор на стороне клиента — `frontend/src/types/api.ts`, тип `ApiFailure`.

## Охрана

Завести **отдельную** пару `api_guard` / `api_require` для префикса `/api/*`,
отдающую JSON.

⛔ Существующие `_guard` (53 вызова) и `require` (41 вызов) на HTML-маршрутах
не трогать: они возвращают `303`, и это правильно для страниц. Одна правка
там задела бы все модули разом.

⚠️ Почему это блокер, а не косметика: `fetch` по умолчанию **идёт** за `303` и
возвращает `200` с HTML формы входа. Экран показал бы пустоту вместо «сессия
истекла», а регистратура решила бы, что у пациента нет записей. Клиент уже
страхуется — `redirect: 'manual'` в `services/api.ts` — но правильное место
решения на сервере.

## Адреса — от бизнес-сущностей, а не от страниц

```
плохо:   GET /api/render-patient-html
хорошо:  GET /api/patients/{id}
         GET /api/patients/{id}/appointments
         GET /api/patients/{id}/teeth
         GET /api/patients/{id}/anamnesis
         GET /api/patients/{id}/documents
```

⛔ `GET /admin/patient/{pid}` — **909 строк одной функцией**, 15 обращений к
базе, расчёты внутри f-строк. Переносить целиком нельзя: разбирается минимум
на 8 ресурсов. ⭐ Побочная польза: эти арифметики сегодня не покрыты тестом
отдельно, только через готовую страницу, — при разборе они впервые получат
собственные проверки.

## Намерение — явным полем

```json
{ "shown": ["sf", "mk", "state"] }
```

⛔ Не различать намерение через `undefined` против `""`. Один и тот же зуб
правят два экрана: детальная одонтограмма шлёт карту поверхностей, диалог фиши
— только буквы. Функция, не различавшая «поля нет» и «поле пустое», молча
переписывала работу первого экрана вторым: пересохранение **без единой правки**
превращало пломбу в кариес на подписываемой 043/e (08-16, две потери данных).

⚠️ Дешёвая проверка на весь класс: **повторный POST того же тела обязан дать
тождественную строку в базе.**

## Расчёты — серверные

React не становится новым источником бизнес-значений. `BOP%` обязан совпадать
с серверным счётом. Если предварительный расчёт нужен для отзывчивости —
сначала написать проверку на совпадение результатов, потом код.

## Проверки, которые обязан повторить каждый новый эндпоинт

Они сегодня лежат в теле HTML-маршрутов, а не в `db.py`:

- запись: `bad`, `bad_name`, `bad_phone`, `bad_off`, `bad_time`, `outside`,
  `outside_doc`, `bad_bd`;
- настройки: `_val_clinic`, `_val_theme`, `_val_hours`, `_val_services`;
- пациенты: IDNP в 13 цифр, цена до 1 000 000, `_PLAN_EDGES` с обязательной
  причиной для `refuzat`, белый список `_OPEN_EXT`, `MAX_DOC_MB`.
