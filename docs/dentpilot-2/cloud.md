# DentPilot Cloud — план v3

⏳ **Контракт и план, не реализация.** Собран 24.09 из плана v2 («Master
Implementation Plan v2», 30 фаз) и разбора того же дня. Опирается на решение
21.09: облачные аккаунт, лицензия и учёт устройств приняты, **в облако уезжает
право пользоваться, а не картотека** ([tasks.md](tasks.md) — P7 и «Чего в
списке нет намеренно»; [i18n.md](i18n.md) §13).

⭐ **Главное решение v3.** v2 строил самообслуживание с первого шага:
регистрация → trial → онлайн-оплата → продление → и только потом лицензия.
Порядок перевёрнут: **сначала файл лицензии и его клиент в программе, потом
оплата, самообслуживание последним.** Причина в коде, а не во вкусе: в движке
сегодня нет ни лицензии, ни grace, ни идентификатора машины (по `bot/app` —
ноль вхождений; P7 говорит то же), а v2 в фазе 18 опирался на «существующую
offline/grace-period логику», которой не существует. Клиент лицензии — самый
длинный пакет, и он едет в клинику тем же релизным поездом, что блоки P, E и F.

Цепочка из фазы 27 плана v2 сохраняется, работа начинается с её конца:

```
Оплата → Подписка → Лицензия → Программа
                        ▲
                 шаг 1 начинается здесь
```

## Что меняется относительно v2

| v2 | v3 | Почему |
|---|---|---|
| 30 фаз, регистрация первой | 3 шага, лицензия первой | клиент лицензии в программе — самая длинная часть |
| trial engine на сервере, регистрация на сайте | trial = файл на месяц (30 дней; до 26.09 — 14), выданный руками или формой | пока продажа личная, регистрация никому не нужна |
| «SEPA / Bank Transfer» | «Transfer bancar» в MDL | Молдова не в SEPA; SEPA — отдельный провайдер для клиник в ЕС, если появятся |
| renewal engine с автосписанием и retry | счёт + напоминания по датам, платит клиника | у местных провайдеров списание по расписанию не гарантировано; продление без него |
| после expired «нет входа в программу» | три состояния, последнее — только чтение | картотека принадлежит клинике; сайт обещает «export … oricând» |
| PostgreSQL + SQLAlchemy + Alembic | SQLite + явные шаги миграций, как в движке (✅ 24.09) | десятки клиник, один процесс; PostgreSQL — когда придёт шаг 3 |
| `/api/v1/downloads/latest` | GitHub Releases остаются единственным источником | второй канал разошёлся бы с `update.py` |
| Notification Service, 13 событий | напоминания одной ежедневной задачей | остальные события появятся вместе с событиями |

## Пять запретов

⛔ **Данные пациентов в облако не уезжают.** Сервер знает клинику, IDNO,
контакт, даты и платежи. Ни одного маршрута, принимающего или отдающего
медицинские данные. Это юридический козырь продукта ([i18n.md](i18n.md) §13,
acord furnizor).

⛔ **Движок не переписывается.** Вклад в `bot/app` — один модуль чтения файла,
одна проверка в существующих воротах, один баннер, одна серверная страница.
Расписание, картотека, печать, установщик, обновления, offline-режим не
трогаются.

⛔ **Программа не считает пробный период сама.** Срок всегда приходит в
подписанном файле с сервера. Переустановка и перевод часов не должны ничего
продлевать.

⛔ **Стены на входе нет.** Клиника всегда может открыть карту, распечатать
043/e, выгрузить архив и сделать бэкап — в любом состоянии лицензии. Замок
стоит на записи, не на чтении.

⛔ **Второго канала выдачи файлов нет.** Установщик и exe живут в GitHub
Releases, откуда их берёт `update.py` (четыре источника разведки,
[updates.md](updates.md)). Сайт и кабинет только ссылаются.

## Три состояния программы

Состояние выводится из двух дат файла и текущего времени и нигде не хранится:

| Состояние | Условие | Что работает | Что видит клиника |
|---|---|---|---|
| `active` | сейчас < `valid_until` | всё | ничего |
| `grace` | `valid_until` ≤ сейчас < `grace_until` | всё | баннер директору: «Abonamentul a expirat la … — N zile pentru plată» |
| `readonly` | сейчас ≥ `grace_until` | чтение, печать, экспорт, бэкап, вход, импорт лицензии | баннер всем ролям, кнопки записи выключены, POST отвечает `license_readonly` |

Два особых входа:

- **`missing` на пустой картотеке** — свежая установка. Единственный случай
  стены: показывать нечего, открывается серверная страница активации
  `/admin/license` (класс экрана — как `/admin/recover`, `main.py:411`, но с
  выбором файла и контактами).
- **`missing` или `invalid` на картотеке с пациентами** — клиника, обновившаяся
  до версии с лицензией. ⛔ Не стена: ведёт себя как `grace`, отсчёт 14 дней от
  первого запуска этой версии (дата запоминается там же, где пол часов, см.
  ниже), потом `readonly`. Это принцип [split-contract.md](split-contract.md):
  «не отказывать в запуске, когда показывать есть что».
- **Файл стёрт или испорчен ПОСЛЕ того, как был принят** — льготы заново нет:
  программа живёт по датам последнего принятого файла (они в памяти), в
  `grace` с баннером «restore the file» до их конца, потом `readonly`.
  `active` без файла не бывает. Это закрывает лазейку «стереть файл и
  получить 14 дней» (✅ L3).

⭐ **Политика живёт в файле, не в программе.** `grace_until` выдаёт сервер: у
оплаченной подписки это `valid_until + 14 дней` (те самые две недели
договора), у пробного файла — 3 дня, ровно на перевод (✅ 24.09).
Программа никаких сроков не знает и не конфигурируется.

### Где стоят ворота (✅ L4)

Ворота — одна проверка в шлюзе `_recovery_gate` (`bot/app/main.py`), рядом
с режимом восстановления и `CONFIG_BROKEN`, **до маршрутизации**: пишущий
метод под `/admin` или `/api/` в состоянии `readonly` → страницам 303 на
`/admin?msg=license_readonly`, JSON — `msg_json(False, "license_readonly",
status=423)`. Один код на оба ответа, текст — из `MSG_BANNER`, как у всех
отказов.

⭐ Именно шлюз, а не `_guard`/`api_guard`, как стояло в плане до L4: FastAPI
разбирает тело ДО обработчика, и ворота внутри него ответили бы 422 «неверные
данные» раньше отказа на половине маршрутов — клиника читала бы не ту
причину, а табличный тест не отличил бы одно от другого. Решение —
`license.refuses(path, method)`, чтение (`GET`, `HEAD`, `OPTIONS`) открыто
всегда, облако и демо без ключа ворот не видят (`current()` там None).

Белый список — `license_state.READONLY_ALLOW`, шаблоны маршрутов ровно как в
декораторах, трёх родов:

| Род | Маршруты |
|---|---|
| доступ | вход, установка и смена PIN, восстановление, учётки, `/admin/security/ack` |
| права клиники на свои данные | бэкап, выгрузка пациента (закон 195), право на стирание, открыть документ, шифрование картотеки |
| обслуживание программы | обновление, проверка системы, сеть (LAN), подтверждение раскладки |

Всё, что трогает картотеку, расписание, врачей, прайс и профиль клиники, в
списке не значится — и потому отказывает. Канал записи `/chat` стоит вне
ворот намеренно: пациенту нужен ответ словами бота, а не 303 на журнал —
это L5/L6.

⛔ Список — константа, а не флаг у маршрута. Сторож
`tests/test_structure.py` держит три якоря: шлюз зовёт `refuses`, кортеж
`READONLY_ALLOW` только из адресов под `/admin` и `/api/`, строка кода
отказа живёт только в четырёх файлах ворот (второе решение про readonly в
маршруте — красное). Табличный тест `tests/test_license_gate.py` берёт все
пишущие маршруты из карты экранов и на просроченном файле требует от каждого
либо места в списке, либо отказа; на действующем файле — отказа ни от кого.

⚠️ Только настольное издание: `db.IS_SQLITE`. Облачное издание и демо без
ключа (`api.py:134`, `auth.py:340`) файла не имеют и ворот не видят.

### Баннер, страница активации и клиент (✅ L5)

Баннер — сосед `_tamper_banner` и `_split_banner` в `bot/app/core/layout.py`:
`_license_banner()`, льгота — директору (warn), режим чтения — всем (err),
без файла — с причиной словами. Он стоит в каркасе страницы над `{body}`, а
React монтируется внутри `{body}` (`REACT_MOUNT_MARK`), поэтому баннер виден
на каждом экране, старом и новом, без единой строки в клиенте.

Страница `/admin/license` — того же класса, что восстановление: своя вёрстка,
открывается без бандла. Показывает состояние словами, реквизиты принятого
файла, контакты (`FEEDBACK_EMAIL`, `SUPPORT_PHONE` в layout.py — менять вместе
с сайтом) и форму импорта: файл или вставленный текст. Вход нужен всем,
импорт — директору; регистратура видит просьбу позвать директора, а не петлю
`no_access` → стена. Импорт: сначала галочка условий (`terms`; без неё —
`license_terms`, файл не читается), затем проверка тем же `open_envelope`,
отказ своим кодом (`license_malformed`, `license_key_unknown`,
`license_bad_signature`, `license_older`) обратно на страницу, приём —
атомарная запись рядом с `clinic.json`, `refresh()`, 303 в журнал с
`license_ok` и строка в летописи клиники «Licența a fost activată: valabilă
până la …; acceptați Termenii și condițiile din `TERMS_VERSION`» с именем
директора (26.09: акцепт договора, п. 1 условий).

Стена — в том же шлюзе, что ворота: пустая картотека без годного файла →
каждый GET под `/admin` ведёт на `/admin/license`, кроме входа, установки PIN,
выхода и восстановления. Запись за стеной отвечает `refuses()` кодом
`license_missing`, а не редиректом без объяснения. `/api/license` отдаёт
`{applies, state, code, wall, valid_until, grace_until, clinic, plan, seq,
renew}` (`renew` — с L13: последняя попытка автообновления или `null`).

⭐ **Без ключа выдачи лицензия не применяется** (`license.applies()`):
запуск из исходников, песочница `dev up` и exe до первого боевого ключа (L7)
не видят ни стены, ни баннера, ни отказов, а `/api/license` отвечает
`applies: false`. Иначе стена заперла бы каждую свежую установку без двери, а
у разработчика кричала бы каждая страница. Тесты подкладывают ключ окружением
и проверяют всё поведение; в exe ключи вшиты, и рубильника нет.

⭐ **Кнопки клиент не выключает.** Сервер отказывает, конверт несёт текст
из `MSG_BANNER`, а экраны уже показывают `err.text` в плашке — человек читает
причину там, где нажал. Серое поле на 25 экранах — украшение шага 3, а не
условие продажи; мёртвая кнопка без объяснения хуже живой с отказом.
React-клиент **сам сроков не считает** — два вычислителя разошлись бы, как
расходились статусы плана.

## Файл лицензии

```
DATA_ROOT\license.json     выдан сервером, подписан
DATA_ROOT\license.state    пол часов, дата первого запуска версии
```

**Место** — то же, что у `device.json` по P7 ([tasks.md](tasks.md):982):
корень папки `clinic.json` (`paths.data_root()`, `bot/app/paths.py:46`), не
внутри `data\`, вне белого списка бэкапа (`backup.py:96-111`). Файл
переживает переустановку и **не уезжает в архив**: клиника на новой машине
импортирует его заново (он у неё в письме) — в шаге 2 программа заберёт его
сама. В режиме `clinic_client` ([deployment-modes.md](deployment-modes.md))
файла нет: лицензию держит машина с картотекой.

### Схема (L1, ✅ 24.09)

Файл — JSON-объект в UTF-8 без BOM. Конверт:

| Поле | Тип | Правило |
|---|---|---|
| `v` | int | `1`; другое — `license_malformed` |
| `kid` | str | `^[a-z0-9-]{1,16}$`; ключ выдачи, ищется в таблице программы |
| `payload` | str | base64url без `=` (RFC 4648 §5): байты JSON-документа claim |
| `sig` | str | base64url без `=`: подпись RSA над байтами `payload`, ровно 384 байта |

Лишние поля конверта программа не читает. Претти-печать конверта роли не
играет: подпись стоит на байтах `payload`, а не на файле.

Claim — `payload` после раскодирования, JSON-объект:

| Поле | Тип | Правило |
|---|---|---|
| `clinic_id` | str | `^c_[0-9a-f]{12}$`; выдаёт сервер, у клиники один навсегда |
| `clinic` | str | название для баннера, 1–120 знаков |
| `idno` | str | 13 цифр; пусто разрешено только при `plan = trial` |
| `plan` | str | `trial` или `standard` |
| `country` | str | ISO 3166-1 alpha-2, сегодня `MD` — claim из [i18n.md](i18n.md) §13 |
| `seq` | int | ≥ 1; у клиники строго растёт с каждой выдачей |
| `issued_at` | str | `YYYY-MM-DDTHH:MM:SSZ`, UTC |
| `valid_until` | str | тот же формат; `> issued_at` |
| `grace_until` | str | тот же формат; `≥ valid_until` |
| `renew` | obj | необязательно (✅ L13): `{"url": "https://…", "token": "…"}`, токен ≥ 32 знаков; `http://` принимается только на loopback — стенд и сервер на том же ПК |

Сервер пишет claim одним способом — `json.dumps(claim, ensure_ascii=False,
separators=(",", ":"), sort_keys=True)` — чтобы выдача была воспроизводимой.
⛔ Программа этим правилом не пользуется: она проверяет байты, какие пришли, и
только потом разбирает JSON; канонизация на стороне проверки — второй парсер,
который однажды разойдётся. Неизвестные поля claim программа пропускает,
подпись их всё равно покрывает.

Политика — в датах, не в коде программы: `standard` — `grace_until =
valid_until + 14 дней`; `trial` — `valid_until = issued_at + 30 дней` (с 26.09, «Prima lună — gratuită» сайта; было 14),
`grace_until = valid_until + 3 дня` (✅ 24.09).

### Подпись и проверка (✅ 24.09: RSA через `pow`)

RSA-3072, `e = 65537`, PKCS#1 v1.5 поверх SHA-256. Схема 21.09 — подписанный
claim и ключ, вшитый в программу, — не менялась, менялся только алгоритм:
Ed25519 в exe потребовал бы либо вендорить кривую, либо `cryptography`
третьим исключением после `pyzipper` и `sqlcipher3`
(`bot/requirements-desktop.txt`); здесь хватает стандартной библиотеки.

Проверка — по шагам и в этом порядке, `bot/app/core/rsa_verify.py` (L2):

1. конверт: объект, `v == 1`, четыре поля нужных типов — иначе
   `license_malformed`;
2. `kid` есть в таблице ключей программы — иначе `license_key_unknown`;
3. `payload` и `sig` раскодировать строго (только алфавит base64url, длина
   `sig` = 384) — иначе `license_malformed`;
4. `s = int(sig)`; `s < n`, иначе `license_bad_signature`; `em = pow(s, e, n)`
   как 384 байта;
5. построить ожидаемый блок `00 01` + `FF`×330 + `00` +
   `3031300d060960864801650304020105000420` + SHA-256(`payload`) и сравнить с
   `em` через `hmac.compare_digest` — иначе `license_bad_signature`;
6. только теперь разобрать `payload` как JSON и проверить claim по таблице —
   иначе `license_malformed`.

⛔ Расшифрованный блок не разбирать — только сравнивать с построенным: разбор
паддинга — тот класс ошибок, из которого сделан Bleichenbacher. ⛔ Не PSS: ему
нужен MGF1, ещё один слой кода ради свойства, которое здесь не покупается.
Замер времени не нужен: при `e = 65537` проверка занимает микросекунды.

Публичные ключи — таблица `KEYS = {kid: (n, e)}` константой в
`rsa_verify.py`; ротация = новый `kid` в следующем релизе и файлы под новым
ключом после того, как релиз доехал до клиник. Первый боевой ключ ложится в
таблицу с L7, до тех пор она пуста. Приватный ключ есть только у сервера
(`cloud/app/license.py`, `cryptography` там уместна).

✅ **Тестовый ключ (решение L2).** `open_envelope(text, keys)` получает
таблицу АРГУМЕНТОМ и про окружение не знает; тесты движка передают ключ
`test` из фикстур прямо в вызов. В программе таблицу собирает `license.keys()`
(✅ L3, чистая часть — `license_state.keys_from`): `KEYS` плюс, только при
`not paths.is_frozen()`, ключи из `DENTART_LICENSE_KEYS` (путь к JSON с `kid`,
`n`, `e`; годится и список) — так тесты с живым сервером подкладывают ключ
через окружение харнесса. ⛔ В собранном exe
переменная не читается вовсе: `sys.frozen` ставит PyInstaller, и снять его
из `dental.env` нельзя. Результат проверки — `Claim` с датами в UTC; всё, что
про время и состояния, начинается после него (L3).

**Пол часов и память (✅ L3).** Перевод часов назад не должен оживлять файл.
Программа не верит времени раньше, чем `max(issued_at, last_seen)`, где
`last_seen` — последняя виденная дата. Это защита от случайного и ленивого, не
DRM: продажа личная, рынок маленький, а сервер в шаге 2 при каждом выходе в
сеть приносит своё время.

Состояние не хранится — выводится из дат и часов при каждом вопросе
(`license.current()`), поэтому полночь, на которой кончился срок, видна первому
же запросу без перезапуска. Хранится только память, `license.state` рядом с
файлом:

| Поле | Что помнит | Правило слияния с зеркалом |
|---|---|---|
| `first_start` | первый запуск версии с лицензией — отсчёт для клиники без файла | самое раннее |
| `last_seen` | последнее виденное время — пол часов; пишется на старте и раз в сутки | самое позднее |
| `accepted_seq` | seq последнего принятого файла; файл с меньшим seq — `license_older` | больший seq |
| `valid_until`, `grace_until` | даты последнего принятого файла — по ним живут без файла | вместе с seq |

Зеркало — `lic_first`, `lic_seen`, `lic_accepted` в `schema_meta`: файл памяти
стереть проще, чем базу, а архив, восстановленный на новой машине, приносит с
собой и то, что программа уже приняла. Запись атомарная, тем же приёмом, что
`auth.json`; битая память читается как пустая, а не роняет старт.

**Как файл попадает в программу.** Шаг 1: страница `/admin/license` —
выбрать файл или вставить его содержимое; письмо с файлом отправляет сервер.
Шаг 2 (✅ L13, раздел ниже): программа сама спрашивает `renew.url` раз в сутки
(тот же приём, что `update.check_async`: без блокировки старта, с таймаутом,
молча при отказе) и заменяет файл, если пришёл `seq` выше.

### Автообновление файла (✅ L13, 25.09)

Файл, выданный сервером с публичным адресом, несёт `renew`: адрес
`/v1/license` этого сервера и токен клиники. Токен рождается с первой
выдачей и дальше один и тот же — сменить его значит оставить без обновления
все файлы, что уже у клиники (отзыв токена — шаг 3, если понадобится).

Провод — `core/license_renew.py`, чистый, как `rsa_verify`; решение —
`core/license.py`:

```
GET {renew.url}?seq={принятый seq}      Authorization: Bearer {renew.token}
200 — тело и есть файл (тот же текст, что скачивается и уходит письмом)
204 — новее принятого у сервера нет
401 — токен не признан
всё остальное — «сервера нет»: сеть, таймаут, 5xx, редирект, тело больше 64 КБ
```

- ⛔ **Замена только на `seq` выше принятого**, и только после того же
  `open_envelope` с той же таблицей ключей, что у файла из письма: сервер —
  свидетель, а не судья. Файл старее, тот же, с битой подписью, под чужим
  ключом — диск не тронут, состояние прежнее.
- ⛔ **Сервера нет — программы это не касается.** Запрос идёт задачей на
  цикле событий после `startup()`, сеть — в потоке с таймаутом 10 с;
  `/health` и первый экран его не ждут. Отказ — строка в лог, без баннера:
  программа живёт по файлу на диске и по памяти («Пять запретов»).
- **Раз в сутки** от старта процесса (`RENEW_EVERY`), плюс кнопка «Verifică
  acum dacă există un fișier nou» на `/admin/license` — директору, тем же
  запросом, с ответом словами (`license_renewed`, `…_same`, `…_offline`,
  `…_refused`, `…_bad`, `…_none` в `MSG_BANNER`). `POST /admin/license/renew`
  стоит в `READONLY_ALLOW`: новый файл нужен именно в режиме чтения.
- Принятый с сервера файл — строка летописи «Licența a fost reînnoită
  automat…»; `/api/license` отдаёт `renew: {at, outcome, seq}` последней
  попытки этого процесса (`null`, если в файле нет `renew`); страница
  лицензии называет последнюю проверку словами.
- ⛔ Редиректам клиент не следует: токен не должен уехать на чужой адрес.
  `renew.url` — `https://`; `http://` программа принимает только на loopback,
  и сервер пишет поле только на адрес, который пройдёт это правило
  (`license.renew_offered()`; `python -m app.tools check` говорит, что есть).

Сервер: `clinics.renew_token`, `renew_at`, `renew_seq` (миграция 2); каждый
запрос оставляет в карточке «программа спрашивала … файл у программы» — по
нему видно, дошёл ли до клиники файл после платежа, а список предупреждает,
пока не дошёл; выдача файла программе — строка `renew` в журнале, 204 журнал
не пишет. Письмо с файлом говорит активированной программе, что делать
ничего не нужно.

Доказано живым движком со стендом сервера в процессе теста
(`tests/test_license_renew.py`): старт не ждёт стенд, который держит ответ
три секунды; новый файл принят без перезапуска; файл старее, тот же, битый,
204, 401, 500, порт закрыт — диск и состояние прежние, запись работает;
кнопка в readonly проходит ворота и возвращает работу; регистратуре кнопка
закрыта. Живым сервером лицензий (`cloud/tests/test_renew.py`): клиент
программы, загруженный по пути, получает файл 1, 204 на тот же seq, файл 2
после подтверждения платежа, 401 на чужой токен; адрес не https и не loopback
— поле не пишется, письмо не обещает. Пары, на которых стенд был красным:
без сравнения `seq` файл 4 ложился поверх 6; без проверки подписи стенд
подсовывал битый файл; запрос на цикле событий задерживал старт.

## Сервер

Отдельная программа в `cloud/`, свой `requirements.txt`, свои тесты, свой
Dockerfile. ⛔ Ни одного импорта из `bot/`: движок — одна клиника на процесс,
кода многоклиничности в нём нет и не будет. Общее с движком — только этот
документ и вектор контракта.

```
cloud/app/main.py       FastAPI: админка (без React), /v1/license (✅ L13), callback maib (L12)
cloud/app/db.py         SQLite (WAL) + шаги миграций тем же приёмом, что db.py движка
cloud/app/license.py    выдача: payload → подпись приватным ключом → seq+1 → запись в issues
cloud/app/jobs.py       ежедневная задача: состояния, напоминания, письма
cloud/app/mail.py       SMTP, шаблоны на румынском
cloud/tests/            свой прогон в стиле tests/harness.py: сервер на свободном порту, временная база
```

**Таблицы:** `clinics` (id, name, idno, contact_name, email, phone, address,
created_at) · `subscriptions` (clinic_id, plan, price, currency, valid_until,
grace_days, cancelled_at) · `payments` (id, clinic_id, amount, currency,
method, status, reference, months, provider_id, created_at, paid_at,
confirmed_by) · `issues` (clinic_id, seq, kid, payload, sig, issued_at,
reason) · `reminders` (subscription_id, kind, period, sent_at) · `audit` (who,
what, clinic_id, at, detail) · `admins` (login, hash, …).

⭐ **Состояние подписки не хранится — выводится** из `valid_until` и
`grace_days` тем же правилом, что в программе. `trialing`, `active`,
`past_due`, `expired` из v2 — это отчёт, не колонка: колонка со статусом
расходится с датами при первом же ручном правлении.

**Продление.** Подтверждённый платёж на N месяцев двигает `valid_until` на N
месяцев от `max(сегодня, valid_until)`: ранняя оплата не крадёт дни, поздняя
не дарит. Каждое продление = новая выдача файла (`seq+1`) и письмо с ним.

**Ключи.** Приватный ключ — только на сервере, в файле с правами 0600 вне
репозитория и вне образа, путь через переменную окружения `DP_LICENSE_KEY`.
Публичный — в программе. ⛔ Ключ в репозитории, в `docker-compose.yml` или в
письме — нет. ✅ L7: `python -m app.tools keygen --kid 2026a --out
/srv/dentpilot/keys/2026a.pem` пишет PEM с правами 0600 и печатает строку для
`rsa_verify.KEYS` — единственное, что уезжает в программу; тестовый ключ
сервер читает из того же `tests/fixtures/license/test-key.json`, что и тесты
движка.

**Админка.** Один администратор, пароль (Argon2id или `pbkdf2-sha256` с
параметрами из `auth.py:59`, обе стойкие), кука сессии, проверка Origin на
POST тем же приёмом, что `same_origin_post`, лимит попыток входа. Экраны:
клиники · клиника (подписка, платежи, выдачи, аудит) · платежи в ожидании ·
выдать файл · журнал. Всё серверное: это инструмент одного человека, React
ему не нужен.

**Хостинг.** VPS, Caddy с автоматическим TLS, `cloud.dentpilot.md` (✅ 24.09).
Сайт остаётся статикой на GitHub Pages и только ссылается. Бэкап — копия
файла базы раз в сутки в другое место плюс учение по восстановлению до
первого клиента. ✅ L10: пошагово в `cloud/DEPLOY.md`, файлы в
`cloud/deploy/`, команды `app.tools check / backup / verify-backup / drill`;
три вещи восстанавливают сервис на чистой машине — `cloud.env`, PEM-ключ и
последняя копия базы.

**Почта.** Шаг 1 — SMTP существующего ящика с паролем приложения, десятки
писем в месяц. Транзакционный провайдер — когда появится доменная почта или
объём.

## Оплата

### Шаг 1 — transfer bancar

```
админ создаёт платёж → reference DP-2026-000001 → письмо клинике с реквизитами и reference
клиника платит, указывая reference в назначении
админ видит поступление в банке → Confirm → продление → новый файл → письмо
```

`reference` уникален (год + порядковый номер), печатается в письме и в
админке. Confirm идемпотентен: второе подтверждение того же платежа — отказ, а
не второе продление. Reject оставляет запись со статусом `rejected` и
причиной. Каждое действие — строка в `audit`.

### Шаг 2 — maib (✅ L12, 25.09)

Один провайдер даёт карты, Apple Pay и Google Pay сразу, если брать
hosted-страницу оплаты. Инварианты не зависят от имён методов в их API (имена —
по документации на момент реализации):

1. создать платёж у maib → получить адрес страницы → отправить клинике;
2. callback принять, подпись проверить **и всё равно** запросить статус
   платежа у maib по его id — источник истины сервер провайдера, не редирект и
   не callback сам по себе;
3. `provider_id` уникален в `payments`: второй callback того же платежа — ничего
   не делает;
4. `paid` → продление → файл → письмо, той же функцией, что и для перевода;
5. mock-провайдер существует только в тестах, ⛔ прод его не знает вовсе.

Без автосписания: за 14 дней до `valid_until` сервер создаёт платёж и шлёт
ссылку, клиника платит когда хочет.

⚠️ Заключает ли maib договор эквайринга с антрепренором-независимым, а не
только с SRL, — по-прежнему вопрос Олега; код написан так, что до ответа
ничего не меняется: три `DP_MAIB_*` пусты — карт нет, платежи переводом, как в
шаге 1. И у бухгалтера: какой документ выдавать на оплату картой и на перевод
— это определяет, что печатает счёт (шаг 3).

**Как сделано (L12).** Провод к maib — `cloud/app/maib.py`, и только он знает
имена их API (документация maib ecommerce API v2 на 25.09 — по памяти, сайт
из облачной сессии недоступен; ⚠️ сверить в песочнице: `generate-token`,
`pay`, `pay-info/{payId}`, callback `{"result", "signature"}`, подпись
`base64(sha256(значения result по алфавиту ключей через «:» + «:» +
signatureKey))`). Ошибка в именах не пропустит чужие деньги: истина о платеже
спрашивается у maib отдельно, и только его `OK` продлевает.

- **Долг один.** Ссылка на карту — свойство того же платежа с тем же reference
  (`payments.provider_id` = payId, `pay_url`, миграция 3): письмо несёт ссылку
  на hosted-страницу и, если есть реквизиты, перевод с reference. Ссылку
  получает платёж «картой» из карточки, кнопка «Ссылка на карту» у ожидающего
  перевода и ежедневная задача — к счёту периода, до первого письма. maib
  молчит — платёж откатывается (из карточки) или уходит без ссылки (из
  задачи), reference не тратится.
- **Одно правило на три входа** — `payments.settle(con, платёж, pay-info)`:
  callback `POST /v1/maib/callback`, кнопка «Проверить» и ежедневная задача
  для каждого ожидающего платежа со ссылкой. Callback — только сигнал: подпись
  проверяется (400 иначе), платёж ищется по payId (404, если не наш), и всё
  равно спрашивается `pay-info`; maib не ответил — 503, пусть повторит.
  `OK` → `payments.confirm` той же функцией, что перевод: продление, файл
  `seq+1`, письмо (`license.mail_latest` — одна на админку, callback и задачу);
  не в ожидании → ничего (второй callback); `CREATED`/`PENDING` → ждём; всё
  остальное → платёж остаётся в ожидании со словами maib в `provider_status`
  и строкой `card_failed` в журнале — долг стоит, перевод возможен, «Новая
  ссылка» даёт новый payId на тот же reference.
- Страницы возврата `/pay/ok` и `/pay/fail` не говорят «оплачено»:
  подтверждение и файл — письмом после ответа maib. `app.tools check` берёт
  токен и называет адрес callback; без `DP_MAIB_*` — предупреждение, не
  препятствие.

Проверяется `cloud/tests/test_maib.py` стендом maib в процессе теста (единственное
место, где он есть; подпись стенд считает своей записью правила): ссылка и что
получил maib (orderId = reference, сумма, адреса под `DP_BASE_URL`, токен один
раз), письмо с ссылкой и переводом; callback «OK» при `pay-info` CREATED —
только сигнал; успешный → продление на месяц от прежнего конца, файл принимает
движок, письмо с файлом, журнал; повторный → ничего; четыре битых → 400; чужой
→ 404; «Проверить» на FAILED → ожидание со словами maib, «Новая ссылка» →
новый payId и письмо, затем `OK` → оплачен; `card_none` без ссылки; страницы
возврата; ежедневная задача — ссылка в счёте, оплата замечена без callback от
имени `daily`, срок продлён; maib молчит — письмо с одним reference, платёж из
карточки откатывается, `check` красный; без `DP_MAIB_*` — выбора нет, `no_maib`,
callback 400, всё остальное как в шаге 1.

## Напоминания

Одна ежедневная задача (`cloud/app/jobs.py daily`, из cron), для каждой
подписки — что сегодня отправить. Отправленное пишется в `reminders` с ключом
`(subscription, kind, period)`; повторный запуск в тот же день ничего не шлёт.

✅ L9 (24.09). Строки таблицы — **окна дат** `[с, до)`, не точки: если задача
не бежала несколько дней, она шлёт письмо той строки, в чьём окне сегодня, а
не все пропущенные подряд. Берётся последняя подходящая строка (при льготе 0
в канун срока — «de mâine regim de citire», не «expiră în 3 zile»). `period` —
дата конца срока подписки: продление даёт новый период, и письма по нему идут
заново. Счёт (`valid_until − 14`) — только абонементу: задача берёт открытый
платёж клиники или заводит новый на тот же срок, что оплачивали в последний
раз (иначе 1 месяц по тарифу), и все письма периода несут один reference;
пробному вместо реквизитов — как оформить абонемент. Без `DP_BANK_*` в письме
честная фраза «nota de plată o primiți separat». Клиника без e-mail —
пропуск словами в отчёте задачи, без записи в `reminders`. Каждая подписка —
своя транзакция; каждое письмо — строка `reminder` в журнале, каждый запуск —
строка `daily` с итогом. Та же задача — кнопкой «Запустить ежедневную задачу»
в админке; журнал целиком — `/admin/audit`. Даты в файле и в окнах — UTC,
cron на 06:05 UTC (README).

| Когда | Кому | Письмо |
|---|---|---|
| `valid_until − 14` | оплаченные | счёт на следующий период: reference или ссылка maib |
| `valid_until − 3` | все | «Abonamentul expiră în 3 zile» |
| `valid_until` | все | «Abonamentul a expirat — 14 zile pentru plată» (у пробных свой текст и свой срок) |
| `grace_until − 1` | все | последнее предупреждение: завтра только чтение |
| `grace_until` | все | «Programul a trecut în regim de citire» + как оплатить |
| платёж подтверждён | клиника | новый файл во вложении + что с ним делать |

Тексты румынские, как интерфейс программы. Русская версия — когда появится
клиника, которая попросит.

## Порядок работ

Три шага; каждый заканчивается тем, что можно продать.

```
шаг 1  ядро      файл + клиент в программе + сервер + перевод + напоминания   ← продаётся лично
шаг 2  оплата    maib + автообновление файла + форма пробного периода + кнопка на сайте
шаг 3  кабинет   регистрация, устройства (P7), счета PDF, полная админка, PostgreSQL
```

⭐ Шаг 1 не ждёт блоков P и E, но **едет одним релизом с ними**: клиент
лицензии — изменение в программе, а выпуск программы идёт лестницей
[release.md](release.md). Сервер и админку можно поднять раньше и выдавать
файлы нынешним клиникам вручную ещё до релиза.

### Чего здесь нет намеренно

Регистрация с верификацией почты, кабинет клиники, привязка устройств
(`device.json`, P7), счета PDF, сервис уведомлений, PostgreSQL, дашборд с MRR,
E2E-сценарий фазы 26 — всё это шаг 3 и строится поверх того же файла лицензии
без изменения его формата. Полный список — план v2, он остаётся справочником
по шагу 3.

## Оценка

В неделях чистой работы, с тестами в принятом в проекте виде:

| Часть | Задачи | Недели |
|---|---|---|
| Клиент лицензии в программе, три состояния, релиз | L1–L6 | 1.5–2.5 |
| Сервер, перевод, напоминания, админка, прод, договор | L7–L11 | 1.5–2.5 |
| maib, автообновление файла, форма, кнопка | L12–L15 | 1–1.5 |

Против трёх-четырёх месяцев по v2. Календарь удлиняют не задачи, а ответы:
договор с maib, документ от бухгалтера, сертификат подписи (G2).
