# DentPilot Cloud — план v3

⏳ **Контракт и план, не реализация.** Собран 24.09 из плана v2 («Master
Implementation Plan v2», 30 фаз) и разбора того же дня. Опирается на решение
21.09: облачные аккаунт, лицензия и учёт устройств приняты, **в облако уезжает
право пользоваться, а не картотека** ([tasks.md](tasks.md) — P7 и «Чего в
списке нет намеренно»; [i18n.md](i18n.md) §13).

⭐ **Главное решение v3.** v2 строил самообслуживание с первого шага:
регистрация → trial → онлайн-оплата → продление → и только потом лицензия.
Порядок перевёрнут: **сначала файл лицензии и его клиент в программе, потом
оплата, самообслуживание последним.** Причина в коде, а не во вкусе: в движке
сегодня нет ни лицензии, ни grace, ни идентификатора машины (по `bot/app` —
ноль вхождений; P7 говорит то же), а v2 в фазе 18 опирался на «существующую
offline/grace-period логику», которой не существует. Клиент лицензии — самый
длинный пакет, и он едет в клинику тем же релизным поездом, что блоки P, E и F.

Цепочка из фазы 27 плана v2 сохраняется, работа начинается с её конца:

```
Оплата → Подписка → Лицензия → Программа
                        ▲
                 шаг 1 начинается здесь
```

## Что меняется относительно v2

| v2 | v3 | Почему |
|---|---|---|
| 30 фаз, регистрация первой | 3 шага, лицензия первой | клиент лицензии в программе — самая длинная часть |
| trial engine на сервере, регистрация на сайте | trial = файл на 14 дней, выданный руками или формой | пока продажа личная, регистрация никому не нужна |
| «SEPA / Bank Transfer» | «Transfer bancar» в MDL | Молдова не в SEPA; SEPA — отдельный провайдер для клиник в ЕС, если появятся |
| renewal engine с автосписанием и retry | счёт + напоминания по датам, платит клиника | у местных провайдеров списание по расписанию не гарантировано; продление без него |
| после expired «нет входа в программу» | три состояния, последнее — только чтение | картотека принадлежит клинике; сайт обещает «export … oricând» |
| PostgreSQL + SQLAlchemy + Alembic | SQLite + явные шаги миграций, как в движке | десятки клиник, один процесс; PostgreSQL — когда придёт шаг 3 |
| `/api/v1/downloads/latest` | GitHub Releases остаются единственным источником | второй канал разошёлся бы с `update.py` |
| Notification Service, 13 событий | напоминания одной ежедневной задачей | остальные события появятся вместе с событиями |

## Пять запретов

⛔ **Данные пациентов в облако не уезжают.** Сервер знает клинику, IDNO,
контакт, даты и платежи. Ни одного маршрута, принимающего или отдающего
медицинские данные. Это юридический козырь продукта ([i18n.md](i18n.md) §13,
acord furnizor).

⛔ **Движок не переписывается.** Вклад в `bot/app` — один модуль чтения файла,
одна проверка в существующих воротах, один баннер, одна серверная страница.
Расписание, картотека, печать, установщик, обновления, offline-режим не
трогаются.

⛔ **Программа не считает пробный период сама.** Срок всегда приходит в
подписанном файле с сервера. Переустановка и перевод часов не должны ничего
продлевать.

⛔ **Стены на входе нет.** Клиника всегда может открыть карту, распечатать
043/e, выгрузить архив и сделать бэкап — в любом состоянии лицензии. Замок
стоит на записи, не на чтении.

⛔ **Второго канала выдачи файлов нет.** Установщик и exe живут в GitHub
Releases, откуда их берёт `update.py` (четыре источника разведки,
[updates.md](updates.md)). Сайт и кабинет только ссылаются.

## Три состояния программы

Состояние выводится из двух дат файла и текущего времени и нигде не хранится:

| Состояние | Условие | Что работает | Что видит клиника |
|---|---|---|---|
| `active` | сейчас < `valid_until` | всё | ничего |
| `grace` | `valid_until` ≤ сейчас < `grace_until` | всё | баннер директору: «Abonamentul a expirat la … — N zile pentru plată» |
| `readonly` | сейчас ≥ `grace_until` | чтение, печать, экспорт, бэкап, вход, импорт лицензии | баннер всем ролям, кнопки записи выключены, POST отвечает `license_readonly` |

Два особых входа:

- **`missing` на пустой картотеке** — свежая установка. Единственный случай
  стены: показывать нечего, открывается серверная страница активации
  `/admin/license` (класс экрана — как `/admin/recover`, `main.py:411`, но с
  выбором файла и контактами).
- **`missing` или `invalid` на картотеке с пациентами** — клиника, обновившаяся
  до версии с лицензией, или файл, стёртый руками. ⛔ Не стена: ведёт себя как
  `grace`, отсчёт 14 дней от первого запуска этой версии (дата запоминается
  там же, где пол часов, см. ниже), потом `readonly`. Это принцип
  [split-contract.md](split-contract.md): «не отказывать в запуске, когда
  показывать есть что».

⭐ **Политика живёт в файле, не в программе.** `grace_until` выдаёт сервер: у
оплаченной подписки это `valid_until + 14 дней` (те самые две недели
договора), у пробного файла — короче (предложение: 3 дня, ровно на перевод).
Программа никаких сроков не знает и не конфигурируется.

### Где стоят ворота

Запись уже проходит через два места, и каждый маршрут зовёт одно из них
(правило сторожа «маршруты /api/ охраняет api_guard/api_require»,
`tests/test_structure.py`):

- HTML-формы: `_guard` / `require` — `bot/app/core/auth.py:330`, `:348`;
- JSON: `api_guard` / `api_require` — `bot/app/core/api.py:120`, `:143`.

Ворота лицензии — одна проверка внутри обоих: метод не `GET`/`HEAD` и
состояние `readonly` → HTML: редирект на `/admin?msg=license_readonly`, JSON:
`msg_json(False, "license_readonly", status=423)`. Белый список маршрутов,
которым запись нужна и в `readonly`: вход и выход, смена PIN, бэкап, экспорт
CSV и архива пациента, импорт лицензии, `/admin/security/ack`.
⛔ Список — константа в `core/license.py`, а не флаг у маршрута: сторож
проверяет, что каждый POST-маршрут из [screen-test-map.md](screen-test-map.md)
либо в списке, либо отказывает в `readonly` (табличный тест).

⚠️ Только настольное издание: `db.IS_SQLITE`. Облачное издание и демо без
ключа (`api.py:134`, `auth.py:340`) файла не имеют и ворот не видят.

### Баннер и клиент

Баннер — сосед `_tamper_banner` и `_split_banner` (`bot/app/core/layout.py:649`,
`:670`): `_license_banner()` с одним текстом на состояние. React-клиент
показывает то, что сказал сервер (`/api/license` → `{state, valid_until,
grace_until, clinic}`), выключает кнопки записи в `readonly` и **сам сроков не
считает** — иначе два вычислителя разойдутся, как расходились статусы плана.

## Файл лицензии

```
DATA_ROOT\license.json     выдан сервером, подписан
DATA_ROOT\license.state    пол часов, дата первого запуска версии
```

**Место** — то же, что у `device.json` по P7 ([tasks.md](tasks.md):982):
корень папки `clinic.json` (`paths.data_root()`, `bot/app/paths.py:46`), не
внутри `data\`, вне белого списка бэкапа (`backup.py:96-111`). Файл
переживает переустановку и **не уезжает в архив**: клиника на новой машине
импортирует его заново (он у неё в письме) — в шаге 2 программа заберёт его
сама. В режиме `clinic_client` ([deployment-modes.md](deployment-modes.md))
файла нет: лицензию держит машина с картотекой.

**Формат.** Подпись стоит на байтах, а не на «каноническом JSON»:
канонизация — второй парсер, который однажды разойдётся.

```json
{"v": 1, "kid": "2026a", "payload": "<base64url байтов JSON>", "sig": "<base64url>"}
```

`payload` после раскодирования:

```json
{
  "clinic_id": "c_7f3a…",  "clinic": "ABC Dental",  "idno": "1234567890123",
  "plan": "standard",      "country": "MD",
  "seq": 3,                "issued_at": "2026-10-01T10:00:00Z",
  "valid_until": "2026-11-01T00:00:00Z",
  "grace_until": "2026-11-15T00:00:00Z",
  "renew": {"url": "https://cloud.dentpilot.md/v1/license", "token": "…"}
}
```

- `seq` растёт с каждой выдачей; программа не принимает файл с `seq` ниже
  текущего.
- `country` — тот самый claim из [i18n.md](i18n.md) §13; программа его
  кэширует, расхождение с `clinic.json` = баннер, не перезапись.
- `renew` — шаг 2; пока поля нет, программа сервер не спрашивает.
- `kid` — ключ выдачи. В программу вшиты все действующие публичные ключи;
  ротация = новый `kid` в следующем релизе и файлы под новым ключом после того,
  как релиз доехал до клиник.

**Проверка.** Схема принята 21.09 — Ed25519, ключ вшит. В стандартной
библиотеке Python асимметричной криптографии нет, а `.venv-desktop` держит
правило «ничего лишнего» (`bot/requirements-desktop.txt`), поэтому:

⭐ проверка — на чистом Python в `bot/app/core/ed25519.py`, только verify, с
векторами RFC 8032 в тесте. Порог: проверка при старте укладывается в бюджет
запуска, измерить на машине клиники. Если не укладывается или вендорить кривую
не хочется — запасной вариант, тоже без зависимостей: RSA-3072, PKCS#1 v1.5
поверх SHA-256, проверка = одно `pow(sig, e, n)` и сравнение с ожидаемым
блоком, тридцать строк. `cryptography` в exe — только если оба варианта
отвергнуты: это третье исключение после `pyzipper` и `sqlcipher3`, и оно
весит больше обоих. Решение — L0.

**Пол часов.** Перевод часов назад не должен оживлять файл. Программа не верит
времени раньше, чем `max(issued_at, last_seen)`, где `last_seen` — последняя
виденная дата, записываемая в `license.state` при каждом старте и раз в сутки
и дублируемая в `schema_meta`. Это защита от случайного и ленивого, не DRM:
продажа личная, рынок маленький, а сервер в шаге 2 при каждом выходе в сеть
приносит своё время.

**Как файл попадает в программу.** Шаг 1: страница `/admin/license` —
выбрать файл или вставить его содержимое; письмо с файлом отправляет сервер.
Шаг 2: программа сама спрашивает `renew.url` раз в сутки (тот же поток, что
`update.check_async`, `update.py:477`: без блокировки старта, с таймаутом,
молча при отказе) и заменяет файл, если пришёл `seq` выше.

**Вектор контракта.** `tests/fixtures/license/` — тестовый публичный ключ,
один валидный файл, один с битой подписью, один просроченный. Их читают и
тесты движка, и тесты сервера: формат сходится там, а не в переписке.

## Сервер

Отдельная программа в `cloud/`, свой `requirements.txt`, свои тесты, свой
Dockerfile. ⛔ Ни одного импорта из `bot/`: движок — одна клиника на процесс,
кода многоклиничности в нём нет и не будет. Общее с движком — только этот
документ и вектор контракта.

```
cloud/app/main.py       FastAPI: админка (Jinja, без React), /v1/license, callback maib (шаг 2)
cloud/app/db.py         SQLite (WAL) + шаги миграций тем же приёмом, что db.py движка
cloud/app/license.py    выдача: payload → подпись приватным ключом → seq+1 → запись в issues
cloud/app/jobs.py       ежедневная задача: состояния, напоминания, письма
cloud/app/mail.py       SMTP, шаблоны на румынском
cloud/tests/            свой прогон в стиле tests/harness.py: сервер на свободном порту, временная база
```

**Таблицы:** `clinics` (id, name, idno, contact_name, email, phone, address,
created_at) · `subscriptions` (clinic_id, plan, price, currency, valid_until,
grace_days, cancelled_at) · `payments` (id, clinic_id, amount, currency,
method, status, reference, months, provider_id, created_at, paid_at,
confirmed_by) · `issues` (clinic_id, seq, kid, payload, sig, issued_at,
reason) · `reminders` (subscription_id, kind, period, sent_at) · `audit` (who,
what, clinic_id, at, detail) · `admins` (login, hash, …).

⭐ **Состояние подписки не хранится — выводится** из `valid_until` и
`grace_days` тем же правилом, что в программе. `trialing`, `active`,
`past_due`, `expired` из v2 — это отчёт, не колонка: колонка со статусом
расходится с датами при первом же ручном правлении.

**Продление.** Подтверждённый платёж на N месяцев двигает `valid_until` на N
месяцев от `max(сегодня, valid_until)`: ранняя оплата не крадёт дни, поздняя
не дарит. Каждое продление = новая выдача файла (`seq+1`) и письмо с ним.

**Ключи.** Приватный ключ — только на сервере, в файле с правами 0600 вне
репозитория и вне образа, путь через переменную окружения. Публичный — в
программе. ⛔ Ключ в репозитории, в `docker-compose.yml` или в письме — нет.

**Админка.** Один администратор, пароль (Argon2id или `pbkdf2-sha256` с
параметрами из `auth.py:59`, обе стойкие), кука сессии, проверка Origin на
POST тем же приёмом, что `same_origin_post`, лимит попыток входа. Экраны:
клиники · клиника (подписка, платежи, выдачи, аудит) · платежи в ожидании ·
выдать файл · журнал. Всё серверное: это инструмент одного человека, React
ему не нужен.

**Хостинг.** VPS, Caddy с автоматическим TLS, `cloud.dentpilot.md`. Сайт
остаётся статикой на GitHub Pages и только ссылается. Бэкап — копия файла базы
раз в сутки в другое место плюс учение по восстановлению до первого клиента.

**Почта.** Шаг 1 — SMTP существующего ящика с паролем приложения, десятки
писем в месяц. Транзакционный провайдер — когда появится доменная почта или
объём.

## Оплата

### Шаг 1 — transfer bancar

```
админ создаёт платёж → reference DP-2026-000001 → письмо клинике с реквизитами и reference
клиника платит, указывая reference в назначении
админ видит поступление в банке → Confirm → продление → новый файл → письмо
```

`reference` уникален (год + порядковый номер), печатается в письме и в
админке. Confirm идемпотентен: второе подтверждение того же платежа — отказ, а
не второе продление. Reject оставляет запись со статусом `rejected` и
причиной. Каждое действие — строка в `audit`.

### Шаг 2 — maib

Один провайдер даёт карты, Apple Pay и Google Pay сразу, если брать
hosted-страницу оплаты. Инварианты не зависят от имён методов в их API (имена —
по документации на момент реализации):

1. создать платёж у maib → получить адрес страницы → отправить клинике;
2. callback принять, подпись проверить **и всё равно** запросить статус
   платежа у maib по его id — источник истины сервер провайдера, не редирект и
   не callback сам по себе;
3. `provider_id` уникален в `payments`: второй callback того же платежа — ничего
   не делает;
4. `paid` → продление → файл → письмо, той же функцией, что и для перевода;
5. mock-провайдер существует только в тестах, ⛔ прод его не знает вовсе.

Без автосписания: за 14 дней до `valid_until` сервер создаёт платёж и шлёт
ссылку, клиника платит когда хочет.

⚠️ До кода: заключает ли maib договор эквайринга с антрепренором-независимым,
а не только с SRL. Один звонок, но от него зависит, есть ли шаг 2 вообще. И у
бухгалтера: какой документ выдавать на оплату картой и на перевод — это
определяет, что печатает счёт (шаг 3).

## Напоминания

Одна ежедневная задача (`cloud/app/jobs.py daily`, из cron), для каждой
подписки — что сегодня отправить. Отправленное пишется в `reminders` с ключом
`(subscription, kind, period)`; повторный запуск в тот же день ничего не шлёт.

| Когда | Кому | Письмо |
|---|---|---|
| `valid_until − 14` | оплаченные | счёт на следующий период: reference или ссылка maib |
| `valid_until − 3` | все | «Abonamentul expiră în 3 zile» |
| `valid_until` | все | «Abonamentul a expirat — 14 zile pentru plată» (у пробных свой текст и свой срок) |
| `grace_until − 1` | все | последнее предупреждение: завтра только чтение |
| `grace_until` | все | «Programul a trecut în regim de citire» + как оплатить |
| платёж подтверждён | клиника | новый файл во вложении + что с ним делать |

Тексты румынские, как интерфейс программы. Русская версия — когда появится
клиника, которая попросит.

## Договор

Пункты юристу (acord furnizor уже разводит два отношения — [i18n.md](i18n.md)
§13):

- пробный период 14 дней, без обязательств;
- после окончания оплаченного периода — 14 дней на оплату при полной работе
  программы;
- после них — режим только чтения: картотека, печать, экспорт и бэкап доступны
  всегда;
- файл лицензии выдан одной клинике и не передаётся; перенос на другой
  компьютер той же клиники — импорт того же файла;
- поставщик к данным пациентов доступа не имеет; по данным учётной записи
  клиники (реквизиты, платежи) он оператор в своём праве.

  (G2–G4, [tasks.md](tasks.md)): незнакомой клинике предупреждение SmartScreen
  никто не объяснит голосом.

## Порядок работ

Три шага; каждый заканчивается тем, что можно продать.

```
шаг 1  ядро      файл + клиент в программе + сервер + перевод + напоминания   ← продаётся лично
шаг 2  оплата    maib + автообновление файла + форма пробного периода + кнопка на сайте
шаг 3  кабинет   регистрация, устройства (P7), счета PDF, полная админка, PostgreSQL
```

⭐ Шаг 1 не ждёт блоков P и E, но **едет одним релизом с ними**: клиент
лицензии — изменение в программе, а выпуск программы идёт лестницей
[release.md](release.md). Сервер и админку можно поднять раньше и выдавать
файлы нынешним клиникам вручную ещё до релиза.

### Блок L — задачи

Формат тот же, что в [tasks.md](tasks.md); туда блок переезжает, когда Олег
его примет (счётчик задач там считается по `- [ ]`, поэтому здесь список
живёт отдельно).

- [ ] **L0. Решения Олега.** Ed25519 на чистом Python или RSA через `pow`;
      SQLite или PostgreSQL на шаге 1; льгота пробного файла (3 дня?); домен
      сервера; ящик для писем; периоды продажи (месяц, год?). ⛔ Кода до
      ответов нет: первые два меняют формат файла.
- [ ] **L1. Формат и вектор контракта.** Раздел «Файл лицензии» как схема;
      `tests/fixtures/license/` с тестовым ключом и тремя файлами.
      Проверяется: оба прогона читают одни и те же файлы.
- [ ] **L2. Проверка подписи в программе.** `core/ed25519.py` (или RSA) с
      векторами RFC 8032; замер времени на старте. Проверяется: битая подпись,
      чужой ключ, неизвестный `kid` — три разных отказа.
- [ ] **L3. `core/license.py`.** Чтение файла, пол часов, три состояния плюс
      `missing`/`invalid`, дата первого запуска. Проверяется: тесты с
      подставным временем на каждую границу; перевод часов назад не меняет
      состояния. Файл в тестах лежит в папке `clinic.json` временного сервера
      (`tests/harness.py:77-78`).
- [ ] **L4. Ворота записи.** Проверка в `_guard` и `api_guard`, белый список
      константой, код `license_readonly`. Проверяется: табличный тест по всем
      POST-маршрутам из screen-test-map; правило сторожа + случай в
      `mutate.py`.
- [ ] **L5. Баннер и страница активации.** `_license_banner`, `/admin/license`
      (импорт, статус, контакты), `/api/license`; React показывает состояние и
      выключает кнопки. Проверяется: сцена в браузере (`scripts/tail_shots.py`)
      на каждое состояние.
- [ ] **L6. Существующие клиники.** `missing` на картотеке с пациентами = 14
      дней от первого запуска. Проверяется: база с пациентами без файла
      открывается, баннер есть, стены нет; пустая база — стена.
- [ ] **L7. Сервер: каркас.** `cloud/`, база и миграции, админ-вход, клиники,
      выдача файла, письмо с файлом. Проверяется: выданный файл проходит L2–L3
      в движке.
- [ ] **L8. Платёж переводом.** reference, ожидание, Confirm/Reject, правило
      продления, аудит. Проверяется: двойное подтверждение — отказ; ранняя
      оплата не крадёт дни.
- [ ] **L9. Ежедневная задача.** Состояния, таблица напоминаний, журнал
      отправок. Проверяется: два запуска в один день — одно письмо; подставная
      дата на каждую строку таблицы.
- [ ] **L10. Прод.** VPS, Caddy, домен, ключи, бэкап базы и учение по
      восстановлению. Проверяется: восстановление на чистой машине до первого
      клиента.
- [ ] **L11. Договор и сайт.** Пункты юристу; `privacy.html`/`termeni.html`.
      Проверяется: тексты согласованы с состояниями программы дословно.
- [ ] **L12. maib.** Вопрос о договоре → hosted-страница → callback + проверка
      статуса → идемпотентность → mock только в тестах. Проверяется: успешный,
      повторный, битый и чужой callback — четыре разных исхода.
- [ ] **L13. Автообновление файла.** `renew` в файле, суточный запрос, замена
      по `seq`. Проверяется: сервер недоступен — программа стартует как раньше;
      старый `seq` — файл не заменён.
- [ ] **L14. Форма пробного периода.** На `cloud.dentpilot.md`, лимит по IDNO
      и e-mail, переключатель «выдавать сразу / после одобрения». Проверяется:
      второй запрос с тем же IDNO не выдаёт второй файл.
- [ ] **L15. Кнопка на сайте.** После G2–G4. Проверяется: ссылка ведёт на
      подписанный установщик из GitHub Releases.

### Чего здесь нет намеренно

Регистрация с верификацией почты, кабинет клиники, привязка устройств
(`device.json`, P7), счета PDF, сервис уведомлений, PostgreSQL, дашборд с MRR,
E2E-сценарий фазы 26 — всё это шаг 3 и строится поверх того же файла лицензии
без изменения его формата. Полный список — план v2, он остаётся справочником
по шагу 3.

## Оценка

В неделях чистой работы, с тестами в принятом в проекте виде:

| Часть | Задачи | Недели |
|---|---|---|
| Клиент лицензии в программе, три состояния, релиз | L1–L6 | 1.5–2.5 |
| Сервер, перевод, напоминания, админка, прод, договор | L7–L11 | 1.5–2.5 |
| maib, автообновление файла, форма, кнопка | L12–L15 | 1–1.5 |

Против трёх-четырёх месяцев по v2. Календарь удлиняют не задачи, а ответы:
договор с maib, документ от бухгалтера, сертификат подписи (G2).
