## 17.09.2026 — фундамент и первый экран

Задание Олега (четвёртая редакция, «React migration master prompt») зафиксировало
порядок: фундамент → экраны по одному → Tauri после всех → установщик →
подпись → CI/CD. Он совпадает с планом выше; к Definition of Done экрана
добавились **lint** и **тесты компонентов**.

Сделано одним заходом на экране «Clinica»:

- **API:** `core/api.py` — `api_guard`/`api_require` (401/403 JSON, Origin на
  изменяющих методах), `api_body`; конверт `layout.msg_json` —
  `{ok, code, text, tone, field?, data?}`, где `text`/`tone` берутся из
  `MSG_BANNER` на сервере. `GET`/`POST /api/settings/clinic` в
  `modules/settings/api.py` зовут те же `_val_clinic`/`_finish_cfg`, что форма.
- **Рубильник:** `clinic.json` → `{"ui": {"react": ["settings_clinic"]}}`,
  `layout.react_on`/`react_mount`; `?ui=legacy` отдаёт старую форму на один
  запрос; правка файла руками требует перезапуска (профиль читается при
  старте и при сохранении настроек).
- **Клиент:** `features/settings/ClinicSettingsScreen.tsx` — загрузка / готово /
  пусто (шаблонный профиль) / отказ / нет прав / 401 → вход; `Icon` из
  генерируемого `icons.ts` (`scripts/gen_icons.py`); `Toast` с разметкой
  серверной плашки. Vitest 29 проверок, ESLint (typescript-eslint + хуки).
- **Сторожа:** `test_api.py` (69 проверок на данных), два правила в
  `test_structure` (маршруты `/api/` только через `api_guard`; `icons.ts`
  свежий) с мутациями; `smoke_exe` проверяет бандл; `Build-Desktop.ps1`
  зовёт `npm run build` до PyInstaller; в CI отдельная работа клиента.

⚠️ Первый прогон CI на GitHub (до этих правок) упал дважды одинаково: наборы,
которые читают `dental.db` stdlib-ом сразу после `with Server(dir_=…)`, дали
`disk I/O error` (13, затем 18 из 18), локально — по одному на полный прогон.
Причина в харнессе, не в продукте: сервер гасится TerminateProcess-ом, и
первое открытие базы попадает на ещё не отпущенное отображение `-shm`.
`Server.__exit__` теперь дожидается, пока база откроется (`_settle_db`);
исключение Defender пробовалось и ничего не изменило. Кодировка консоли в
`mutate.py` починена.

⚠️ Известное расхождение со старым экраном: после сохранения через API имя
клиники в сайдбаре обновляется при следующем переходе, а не сразу (старая
форма перезагружала страницу целиком).

## 17.09.2026 — этап 3: настройки, пачка A

Хаб, «Acces din rețea», справка и часы работы — четыре экрана одним заходом,
по порядку Олега (LAN, FAQ, хаб, часы), без правок фундамента.

- **Хаб:** плитки стали данными (`_hub_tiles()`): адрес, иконка, тон, подпись
  и строка состояния кусками (текст / иконка с текстом и тоном / точка
  цвета). Старая страница собирается из них же (`_hint_html`), байт в байт.
- **Сеть:** проза страницы разложена в `lan.py` на куски (`intro_html`,
  `status_html`, `firewall_html`, `tips_html`); переключение — общий
  `_set_lan`, перезапуск — тот же `restart_app`, текст перезапуска — константы
  `RESTART_*`, одни на страницу и на JSON. Кнопка брандмауэра в тестах не
  нажимается (UAC), проверяется только охрана.
- **Справка:** `faq.entries()` — записи данными (имя иконки, вопрос, ответ
  HTML-ом), `render()` рисует из них.
- **Часы:** тот же payload, что слал скрипт страницы, та же `_val_hours`.
- **API:** `GET /api/settings/hub`, `GET/POST /api/settings/lan`,
  `POST /api/settings/lan/firewall`, `GET /api/settings/faq`,
  `GET/POST /api/settings/hours`. Две секции отдают HTML-куски (ответы
  справки, проза сети) — это текст сервера из тех же строк, что у старой
  страницы, не отрисовка страницы через API: кнопки и состояния рисует клиент.
- **Тесты:** `test_settings_api.py` — 5 наборов; старые наборы настроек, сети,
  ролей, темы и перезапуска зелёные после выноса. Клиент: 13 проверок Vitest.

⚠️ Расхождение: на старой странице сети блок «правило брандмауэра» содержит
кнопку внутри рамки; в React кнопка стоит под рамкой (проза с сервера, кнопка
своя). После переключения доступа старая страница показывала отдельный
экран перезапуска, React показывает тот же текст плашкой на месте.

## 17.09.2026 — этап 6: список пациентов (Search)

- **Сначала пин.** Поведение `_pl_rows`/`_pl_filter` записано руками в
  `test_patients_api.suite_parity` на картотеке с каждой веткой статуса,
  долгом и авансом, врачом из фиши и врачом последнего визита, вторым
  номером в заметке, датой рождения и диакритикой: порядок по умолчанию
  (последний визит, потом никогда не бывшие по id), по имени, по долгу,
  фильтры статуса (включающие), врача («-» = без врача), канала, сальдо,
  скрытый архив и его счётчик, варианты фильтров.
- **`GET /api/patients`** считает отбор, порядок и страницу в базе:
  `db.patients_rows` — ОДНА выборка: те же агрегаты, что стояли по одному
  (`patients_visits`, `…_alert_counts`, `…_plan_counts`, `patients_debt`),
  соединённые с `patients`, врач последнего визита — подзапросом по
  индексу (оконная функция `patients_last_doctor` по всей таблице стоила
  ~50 мс на каждый запрос), счёт отбора — `COUNT(*) OVER ()` в тех же
  строках (второй проход ради COUNT стоил столько же, сколько страница);
  `WHERE`/`ORDER BY`/`LIMIT` — базой. Замер на 5 000 фиш и 20 000 записей
  (harness, тот же ПК): старая страница 230–545 мс, API 130–200 мс,
  сводка 82 мс; остаток — агрегат визитов по всей таблице записей, он же
  у старой страницы. Свёртка диакритики и «только цифры» в SQLite — функции
  `dp_fold`/`dp_digits`, зарегистрированные на соединении в `db.init`
  (тот же `fold`, что у Python-фильтра); у PG — `translate(lower())` и
  `regexp_replace`. Статус строки выводит та же `_pl_status`, что рисует
  старая страница; в SQL только включающие предикаты фильтра.
- ⚠️ **Правило отбора живёт в двух местах** — Python старой страницы и SQL
  API — осознанно: старая страница по слову Олега не меняется до конца
  миграции. Расхождение краснеет в `suite_parity` (39 отборов, строка в
  строку: те же id в том же порядке, те же статусы, тот же счёт). С уходом
  старой страницы уйдут и одиночные выборки `_pl_rows`.
- **Вынесено, не скопировано:** разбор строки запроса `_pl_terms` (зовёт и
  `_pl_match_q`), подпись первой карточки `_pl_new_foot`, кусок
  предпросмотра `_peek_html`, правило новой фиши `_new_patient`. Старые
  обработчики стали обёртками, их наборы зелёные.
- **API:** `GET /api/patients?q=&med=&st=&ch=&dat=&sort=&page=&per=`
  (строки с датами уже в поясе клиники, `total/page/pages`, `hidden_arh`),
  `GET /api/patients/summary` (карточки с подписями-кусками, врачи и
  каналы фильтра, статусы с классами, варианты `per`, врачи диалога — один
  раз на открытие экрана), `GET /api/patients/{pid}/peek` (`{html}`, 404),
  `POST /api/patients` (`new_pat`/`dup_pat` с адресом фиши, 422 `bad_pat`).
  Чужие `st`/`ch`/`dat`/`sort`/`per` откатываются к «все»/«по умолчанию»,
  `page` за пределом — последняя, как на старой странице.
- **React `patients_search`:** та же разметка `.pl-*`/`.pp-*` из panel.css;
  буква в поиске ждёт 250 мс, выбор в фильтре идёт сразу, страница

  «Pacient nou» уводит по адресу сервера. `sessionStorage` для панели не

- **Экспорт** остаётся `GET /admin/patients.xlsx` с тем же отбором

- **Тесты:** `suite_parity` (137), `suite_api` (39), `suite_switch` (13);

  `/documents/{id}/delete`, `/appoint`; `GET …/slots`, `GET …/activity`

  фиша целиком: почти каждое действие двигает несколько секций сразу.
- ⚠️ **Находка не про React:** движок опознавал вошедшего только под
  `/admin` (`main._identify`), поэтому любое действие через `/api` подписало
  бы летопись «recepție» и спрятало директорские кнопки. Опознание
  распространено на `/api`; держит `suite_actions` («летопись подписана
  именем вошедшего»).
- ⚠️ **Точка интеграции до C21:** компактная одонтограмма едет куском
  старой страницы (`GET …/teeth` = тот же `odontogram.card`: обе дуги,
  оба вида, подсказка, диалог зуба, мосты). Клиент вставляет кусок и
  пересоздаёт его `<script>` по порядку (innerHTML их не исполняет);
  форма зуба остаётся формой старого маршрута и возвращает страницу с
  `?msg=` — плашку рисует сервер. Кнопка зуба в плане зовёт `openTooth`

- **React `patient_card`:** та же раскладка (`.hero`, `.kpi5`, `.pv2`,

  panel.css), четыре диалога (запись, список за цифрой, просмотр
  документа, отказ); одна функция `act` на все карточки — удача подменяет
  фишу и показывает плашку сервера, отказ отдаёт ошибку форме (поле).
  Черновики форм привязаны к фише, с которой начаты (правило хуков
  запрещает setState в эффекте): свежая фиша после удачи даёт форме свои
  значения, отказ ввод не трогает. `?views=1` — параметр узла и адрес
  через `history.replaceState`. Инлайновые стили старой страницы — классы
  `dp-*` в app.css.
- **Тесты:** `suite_pin` (44), `suite_api` (32), `suite_actions` (56),
  `suite_switch` (14); клиент — 14 проверок экрана.

⚠️ Расхождения со старой фишей: значки способов оплаты внутри `<option>`
не рисуются (браузер и раньше показывал только слово); черновик правки

## Что закрыто и что открыто

**Решено:** порядок работ (граница API раньше оболочки), одна папка вместо
второго репозитория, параллельная разработка с флагами, свой обновлятор вместо
Tauri-обновлятора, Inno вместо NSIS, Windows без Linux и macOS.

**Открыто и решается не кодом:**

- ⏳ **PG-ветка** — в каждой из 109 функций `db.py` два текста SQL. Если
  облако выкидывается, половина слоя данных упрощается; если SaaS в планах —
  ветку беречь. Ни один тест её не исполняет.
- ⏳ **IDNO** — держит одновременно подпись кода, запуск сайта и SMS-пакет.
- ⏳ **Копия базы пилота** для замеров: все выводы о скорости (список
  пациентов, статистика за 366 дней, обе дуги одонтограммы) сделаны чтением
  кода, без единого числа с живых данных.

## Абсолютные правила

1. Движок не переписывать. `db.py`, `engine.py`, `core/auth.py` не трогать ради
   нового интерфейса.
2. Старый HTML в JSX не копировать — компоненты проектировать заново.
3. API не делать отрисовщиком HTML.
4. Origin не менять без отдельного решения.
5. Печать и аварийные экраны в React не переносить.
6. Обновлятор Tauri не включать. Inno автоматически не заменять.
7. `--onefile` не использовать. Сайдкар под LocalSystem не запускать.
8. Старый экран не удалять, пока новый не прошёл пилота и окно отката.
9. Тесты ради миграции не удалять и осмысленное покрытие не уменьшать.
10. Бизнес-правила ради удобства клиента не менять.
11. На боевой базе клиники экспериментов не ставить.
12. Любое изменение поведения — записывать.
