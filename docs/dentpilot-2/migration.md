## 17.09.2026 — фундамент и первый экран

Задание Олега (четвёртая редакция, «React migration master prompt») зафиксировало
порядок: фундамент → экраны по одному → Tauri после всех → установщик →
подпись → CI/CD. Он совпадает с планом выше; к Definition of Done экрана
добавились **lint** и **тесты компонентов**.

Сделано одним заходом на экране «Clinica»:

- **API:** `core/api.py` — `api_guard`/`api_require` (401/403 JSON, Origin на
  изменяющих методах), `api_body`; конверт `layout.msg_json` —
  `{ok, code, text, tone, field?, data?}`, где `text`/`tone` берутся из
  `MSG_BANNER` на сервере. `GET`/`POST /api/settings/clinic` в
  `modules/settings/api.py` зовут те же `_val_clinic`/`_finish_cfg`, что форма.
- **Рубильник:** `clinic.json` → `{"ui": {"react": ["settings_clinic"]}}`,
  `layout.react_on`/`react_mount`; `?ui=legacy` отдаёт старую форму на один
  запрос; правка файла руками требует перезапуска (профиль читается при
  старте и при сохранении настроек).
- **Клиент:** `features/settings/ClinicSettingsScreen.tsx` — загрузка / готово /
  пусто (шаблонный профиль) / отказ / нет прав / 401 → вход; `Icon` из
  генерируемого `icons.ts` (`scripts/gen_icons.py`); `Toast` с разметкой
  серверной плашки. Vitest 29 проверок, ESLint (typescript-eslint + хуки).
- **Сторожа:** `test_api.py` (69 проверок на данных), два правила в
  `test_structure` (маршруты `/api/` только через `api_guard`; `icons.ts`
  свежий) с мутациями; `smoke_exe` проверяет бандл; `Build-Desktop.ps1`
  зовёт `npm run build` до PyInstaller; в CI отдельная работа клиента.

⚠️ Первый прогон CI на GitHub (до этих правок) упал дважды одинаково: наборы,
которые читают `dental.db` stdlib-ом сразу после `with Server(dir_=…)`, дали
`disk I/O error` (13, затем 18 из 18), локально — по одному на полный прогон.
Причина в харнессе, не в продукте: сервер гасится TerminateProcess-ом, и
первое открытие базы попадает на ещё не отпущенное отображение `-shm`.
`Server.__exit__` теперь дожидается, пока база откроется (`_settle_db`);
исключение Defender пробовалось и ничего не изменило. Кодировка консоли в
`mutate.py` починена.

⚠️ Известное расхождение со старым экраном: после сохранения через API имя
клиники в сайдбаре обновляется при следующем переходе, а не сразу (старая
форма перезагружала страницу целиком).

## 17.09.2026 — этап 3: настройки, пачка A

Хаб, «Acces din rețea», справка и часы работы — четыре экрана одним заходом,
по порядку Олега (LAN, FAQ, хаб, часы), без правок фундамента.

- **Хаб:** плитки стали данными (`_hub_tiles()`): адрес, иконка, тон, подпись
  и строка состояния кусками (текст / иконка с текстом и тоном / точка
  цвета). Старая страница собирается из них же (`_hint_html`), байт в байт.
- **Сеть:** проза страницы разложена в `lan.py` на куски (`intro_html`,
  `status_html`, `firewall_html`, `tips_html`); переключение — общий
  `_set_lan`, перезапуск — тот же `restart_app`, текст перезапуска — константы
  `RESTART_*`, одни на страницу и на JSON. Кнопка брандмауэра в тестах не
  нажимается (UAC), проверяется только охрана.
- **Справка:** `faq.entries()` — записи данными (имя иконки, вопрос, ответ
  HTML-ом), `render()` рисует из них.
- **Часы:** тот же payload, что слал скрипт страницы, та же `_val_hours`.
- **API:** `GET /api/settings/hub`, `GET/POST /api/settings/lan`,
  `POST /api/settings/lan/firewall`, `GET /api/settings/faq`,
  `GET/POST /api/settings/hours`. Две секции отдают HTML-куски (ответы
  справки, проза сети) — это текст сервера из тех же строк, что у старой
  страницы, не отрисовка страницы через API: кнопки и состояния рисует клиент.
- **Тесты:** `test_settings_api.py` — 5 наборов; старые наборы настроек, сети,
  ролей, темы и перезапуска зелёные после выноса. Клиент: 13 проверок Vitest.

⚠️ Расхождение: на старой странице сети блок «правило брандмауэра» содержит
кнопку внутри рамки; в React кнопка стоит под рамкой (проза с сервера, кнопка
своя). После переключения доступа старая страница показывала отдельный
экран перезапуска, React показывает тот же текст плашкой на месте.

## 17.09.2026 — этап 6: список пациентов (Search)

- **Сначала пин.** Поведение `_pl_rows`/`_pl_filter` записано руками в
  `test_patients_api.suite_parity` на картотеке с каждой веткой статуса,
  долгом и авансом, врачом из фиши и врачом последнего визита, вторым
  номером в заметке, датой рождения и диакритикой: порядок по умолчанию
  (последний визит, потом никогда не бывшие по id), по имени, по долгу,
  фильтры статуса (включающие), врача («-» = без врача), канала, сальдо,
  скрытый архив и его счётчик, варианты фильтров.
- **`GET /api/patients`** считает отбор, порядок и страницу в базе:
  `db.patients_rows` — ОДНА выборка: те же агрегаты, что стояли по одному
  (`patients_visits`, `…_alert_counts`, `…_plan_counts`, `patients_debt`),
  соединённые с `patients`, врач последнего визита — подзапросом по
  индексу (оконная функция `patients_last_doctor` по всей таблице стоила
  ~50 мс на каждый запрос), счёт отбора — `COUNT(*) OVER ()` в тех же
  строках (второй проход ради COUNT стоил столько же, сколько страница);
  `WHERE`/`ORDER BY`/`LIMIT` — базой. Замер на 5 000 фиш и 20 000 записей
  (harness, тот же ПК): старая страница 230–545 мс, API 130–200 мс,
  сводка 82 мс; остаток — агрегат визитов по всей таблице записей, он же
  у старой страницы. Свёртка диакритики и «только цифры» в SQLite — функции
  `dp_fold`/`dp_digits`, зарегистрированные на соединении в `db.init`
  (тот же `fold`, что у Python-фильтра); у PG — `translate(lower())` и
  `regexp_replace`. Статус строки выводит та же `_pl_status`, что рисует
  старая страница; в SQL только включающие предикаты фильтра.
- ⚠️ **Правило отбора живёт в двух местах** — Python старой страницы и SQL
  API — осознанно: старая страница по слову Олега не меняется до конца
  миграции. Расхождение краснеет в `suite_parity` (39 отборов, строка в
  строку: те же id в том же порядке, те же статусы, тот же счёт). С уходом
  старой страницы уйдут и одиночные выборки `_pl_rows`.
- **Вынесено, не скопировано:** разбор строки запроса `_pl_terms` (зовёт и
  `_pl_match_q`), подпись первой карточки `_pl_new_foot`, кусок
  предпросмотра `_peek_html`, правило новой фиши `_new_patient`. Старые
  обработчики стали обёртками, их наборы зелёные.
- **API:** `GET /api/patients?q=&med=&st=&ch=&dat=&sort=&page=&per=`
  (строки с датами уже в поясе клиники, `total/page/pages`, `hidden_arh`),
  `GET /api/patients/summary` (карточки с подписями-кусками, врачи и
  каналы фильтра, статусы с классами, варианты `per`, врачи диалога — один
  раз на открытие экрана), `GET /api/patients/{pid}/peek` (`{html}`, 404),

  Чужие `st`/`ch`/`dat`/`sort`/`per` откатываются к «все»/«по умолчанию»,
  `page` за пределом — последняя, как на старой странице.
- **React `patients_search`:** та же разметка `.pl-*`/`.pp-*` из panel.css;

- **Экспорт** остаётся `GET /admin/patients.xlsx` с тем же отбором

## 18.09.2026 — этап 10: одонтограмма, UX (C22)

Состав и правила приняты Олегом до начала — [clinical-chart.md](clinical-chart.md)
› C22. Без новых клинических состояний, без правок сервера (в `bot/` не
изменилось ничего, серверные наборы те же), без редизайна.

- **Черновик в `useChart`, не в форме.** Зуб правят ТРИ места — форма, клик
  по поверхности на рисунке и контекстное меню, — поэтому черновик живёт в
  хуке картой по зубу `{base, d}`: `base` — каким зуб был в модели, когда
  правку начали. Клик по соседу правку не теряет (зуб на дуге помечен
  янтарным кольцом `.dirty`, вернёшься — черновик на месте), удачная запись
  меняет `base` — черновик отпадает сам, без счётчика сохранений и без
  эффекта; отказ сервера модель не трогает — ввод остаётся. `ToothForm`
  стала контролируемой (`draft`/`onEdit`), перемонтирование по ключу ушло.
  «Nesalvat» и «Renunță» рядом с «Salvează»; закрыть диалог в фише = сброс.
- **Быстрый цикл:** `pickSurface` — первый клик по поверхности выбирает
  зуб и поверхность, повторный по УЖЕ выбранной крутит состояние по
  `surface_states` сервера: «—» → carie → obturatie → «—» (`cycleState`).
  Работает на дуге и на рисунке инспектора; в фише — нет, диалог модальный.
- **Клавиатура** — обработчик на контейнере `.odop` (tabIndex): стрелки —
  `neighbour()` (ряд / та же позиция другой челюсти, молочные в своей паре),
  фокус переезжает на кнопку зуба; M O D V L — поверхность, P — только на
  верхней; Enter — `save()` черновика, Esc — сброс (в режиме моста — выход
  из него). ⛔ Внутри input/textarea/select и при открытом `dialog[open]` —
  ничего; с Ctrl/Alt/Meta — ничего. Enter и стрелки гасятся, иначе Enter на
  кнопке зуба в фокусе кликнул бы её же. Зуб из `?t=` получает фокус сразу.
- **Контекстное меню** `ToothMenu` (правая кнопка по зубу): состояния
  сервера с отметкой текущего (из черновика) → в черновик, не в базу;
  «Punte nouă de la acest dinte» — режим моста с этим зубом; у молочных
  моста нет; в режиме моста меню не открывается. Те же действия в
  инспекторе: список состояния и кнопка моста от зуба.
- **Отзывчивость** поверх panel.css (её порог 1100 остаётся): ≤1365 —
  инспектор под дугой, ≤1099 — цели поверхностей крупнее (`r: 7.5px` —
  геометрия SVG как CSS-свойство, Chromium/WebView2) и кнопка зуба шире.
- **Кадры Edge** — `scripts/odo_shots.py` (системный Python с
  websocket-client, не CI): двенадцать сцен настоящим вводом через CDP
  (`Input.dispatch*`, не dispatchEvent) и проверки геометрии в странице:
  зубы по порядку без наложений, номер внутри своей кнопки, инспектор не
  пересекает дугу (справа ≥1366, ниже — под ней), скобка по своим зубам у
  своего ряда, выбранная поверхность = подсветка кнопки, без горизонтальной
  прокрутки, меню в окне, консоль чистая. Кадры — `build/shots/odo/`.
- **Тесты клиента:** 16 (цикл, `neighbour`, клавиатура, Enter/Esc с полем
  ввода и открытым диалогом, черновик за зубом, меню и мост от зуба).

⚠️ Намеренно не сделано: подтверждение при уходе со страницы с черновиком
(новая функция), цикл в компактной карточке фиши, цифровые клавиши, клавиши

⭐ **Побочная находка не про продукт, а про СТЕНД:** `tests/harness.py`
поднимал сервер с трубой (`stdout=PIPE`), которую никто не вычитывал. Стоит
серверу напечатать больше буфера окна — 17 КБ трейсбека хватает, — и он
встаёт на `write` навсегда: набор выглядит как «зависло на ровном месте», а
причина не печатается, потому что застряла в той же трубе. Теперь вывод идёт
в файл рядом с песочницей (`Server.log_text()`), и падение при старте
по-прежнему видно.

⭐ **Закрыт пункт контракта, висевший с C21:** инспектор одонтограммы
показывает последний пародонтальный замер выбранного зуба (`perio.tooth_lines`
в модели одонтограммы) и ведёт в тот же осмотр. Фраза собирается на сервере —
по той же причине, что `sfx` у поверхностей. У зуба без замера блока нет.

## 18.09.2026 — правило записи осмотра: сообщаем о ТРОНУТОМ

Решение Олега по последнему открытому пункту этапа 11 — «потеря зуба при двух
рабочих местах». Дыра была НЕ про React: старая форма теряла тот же зуб с
08-25, то есть ровно столько, сколько живёт сама пародонтограмма.

**Что было.** Экран присылал лист ЦЕЛИКОМ и отдельным полем `shown` — «какие
зубы я показывал», — а сервер стирал «показанные, но не присланные».
Показывает лист всегда все 32 зуба, поэтому место, открывшее осмотр раньше,
своим сохранением сносило зуб, который только что измерило второе, а чужие
правки возвращало к числам, которые видело само. Ответ 200 ok_perio, в
летописи обычная вторая строка, на экране ничего.

**Что стало.** Поле называется `covers` и значит другое: «зубы, О КОТОРЫХ это
сохранение сообщает». Стирается `covers` минус присланные — и только это. Зуб
вне `covers` не пишется и не стирается: про него не сказано ничего.

- ⭐ Суть не в имени поля, а в том, что клиент теперь считает НАМЕРЕНИЕ, а не
  показанное. Старая форма снимает слепок листа при загрузке (`wire(col)` в
  CHART_JS) и перед отправкой сравнивает с ним каждую колонку; React сравнивает
  черновик с базой (`usePerio`). Неизменённые «Medic» и «Notă» не отправляются
  вовсе: «поля нет» значит «не сообщали», иначе стала́я вкладка стирала бы
  чужую подпись осмотра тем же способом, каким стирала зуб.
- ⛔ Правило ОДНО на оба интерфейса и живёт в `db.perio_save`: у клиник сегодня
  работает старая форма (React-флаги у пилота выключены), и разойтись двум
  экранам на одних данных нельзя. Обе ветки держит `suite_two_seats`.
- ⭐ **Отпечаток осмотра** (`perio.rev` — sha256 от строк, подписи и заметки;
  колонки в базе НЕТ, миграции тоже) ездит с моделью туда и обратно.
  Разошёлся — запись всё равно проходит, но ответ иной: `ok_perio_merged`,
  «examenul a fost modificat și de pe alt calculator». Это слово, а не замок:
  409 отнимал бы у ассистента набранный лист из 192 чисел ради конфликта,
  которого чаще всего нет — места правят РАЗНЫЕ зубы.
- ⚠️ Зеркальное правило у клиента: при пересадке черновика (`rebase`) зуб,
  которого мы не трогали, берётся У СЕРВЕРА. Без этого чужой зуб, приехавший с
  ответом, показался бы пустым, лист висел бы «несохранённым», а следующая
  запись назвала бы этот зуб тронутым и стёрла его — дыра вернулась бы через
  клиента при исправленном сервере.
- ⚠️ Сообщать нечего — не делается НИЧЕГО, включая строку летописи: пустое
  сохранение это не находка осмотра, а промах по кнопке.
- **Чего решение не закрывает:** если два места правят ОДИН зуб, побеждает
  последний. Молча этого больше не происходит (`ok_perio_merged`), но слияния
  по отдельным точкам нет и не планируется.
- **Проверки.** `suite_two_seats` переписан под новое правило, а не удалён:
  два места через API и та же пара на старой форме, стирание зуба через
  `covers` без `teeth`, отсутствие ложной тревоги на свежем отпечатке, пустое
  сохранение без строки в летописи. В vitest — три: шлём только тронутое,
  очищенный зуб назван в `covers`, чужой зуб переживает следующую запись.
  ⛔ Возврат к «показывали, но не прислали» обязан краснеть.
  ⚠️ JS СТАРОЙ формы наборам недоступен — они шлют поля напрямую, — а решает
  теперь именно он. Его проверяет `scripts\perio_form_check.py` (Edge + CDP,
  не CI, механика от `odo_shots`): слепок листа, сборка `covers`, отказ
  отправлять неизменённые подпись и заметку, чистая консоль.

1. Движок не переписывать. `db.py`, `engine.py`, `core/auth.py` не трогать ради
