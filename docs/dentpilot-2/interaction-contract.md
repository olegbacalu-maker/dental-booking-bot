# Контракт C26.5.3 — расписание как рабочая поверхность

Порядок задан Олегом 19.09: `a` данные карточки → `b` диалог визита → `c`
пустой час → `d` заметка → `e` запись по клику → `f` перетаскивание → `g`
сцена. Причина порядка не в удобстве: диалог сперва обязан иметь правильную
модель состояния, а запись и перетаскивание — это уже КОМАНДЫ.

Главный критерий, его же слова: **у React не может быть собственного
локального мира расписания.** После любого действия источник истины — сервер:
команда → мутация → каноническое живое состояние → обновление React. Два
рабочих места обязаны прийти к ОДНОМУ каноническому состоянию, а не показать
каждое локально правдоподобный результат.

Одной фразой, что из этого следует: **панель получает команды, но не получает
состояния.** Состояние выпускается ровно одной дверью — `live_reply` вместе со
своим отпечатком — и въезжает на экран ровно одной — `case 'apply'` в
`hooks/useLive.ts`. Остальное здесь — следствия.

⚠️ Разведка: четыре читающих агента по поверхностям (чего хотят три диалога,
три варианта данных карточки, командный путь, граница владения с `panel.js`),
ни одной правки. Всё, помеченное ⭐, перепроверено по коду.

## 1. Данные карточки: поля в БЛОК, а не вторая структура

Диалог панели питается блоком канвы. В `day.appt_view` дописываются три
недостающих поля — `doctor` (СНИМОК имени из записи, а не имя колонки),
`pid`, `rec`, — и `st` карточки переименовывается в `status`: в блоке это поле
уже так зовётся, и два имени одного состояния в контракте, который пишется
ради одного канонического состояния, — это ровно 08-12 и 08-16.

⛔ **Что убивает вариант «`cards` в конверт».** `_collect_cards` намеренно
несёт ОТМЕНЁННЫЕ записи, а нажать их на панели негде: канва их отбрасывает,
повестка тоже, списка дня на `/admin` нет. Всё, что попало в конверт, попало в
отпечаток. Значит правка комментария у отменённого визита со второго рабочего
места начала бы отдавать `200` вместо `204` и гнать перерисовку, в которой в
DOM не меняется ничего, — и обратная сторона критерия C26.5.2 («отпечаток
двинулся ⇒ на экране что-то изменилось») перестала бы быть верной. Плюс мина:
у `_collect_cards` ключи словаря **int**, а `live_canon` идёт с
`sort_keys=True` — смешанные ключи дают `TypeError`, то есть 500 на живом
канале.

⛔ **Что убивает вариант «карточка по требованию».** Она живёт ВНЕ протокола
отпечатка, и `hold` к ней неприменим по построению: он защищает только то, что
приезжает конвертом. Пока диалог открыт, правка со второго места двигает
отпечаток, панель перерисовывается — а текст в диалоге прежний, и «Salvează»
кладёт старое поверх нового. Обе стороны видят `ok_comment`. Это буквально
08-16.

⚠️ Цена принятого варианта, названная явно: `doctor`/`pid`/`rec` поедут и в
модель ДНЯ (`appt_view` общая) и там продублируют `cards`; `pid` станет третьей
копией — он уже есть в повестке. ⛔ Сшивать блок с повесткой по `id` в клиенте
запрещено: неявная связь двух структур умрёт молча в день, когда повестку
начнут фильтровать. ⛔ `cards` из модели ДНЯ не убирается: «Lista zilei»
показывает отменённые, и блока у них нет.

⭐ `CardDialog` принимает узкий вид `VisitCardView`, под который структурно
ложатся и `DayCard`, и `DashAppt`. Второго компонента диалога не заводить.

## 2. Состояние диалога: React владеет НАМЕРЕНИЕМ, сервер — ФАКТОМ

В React живёт только то, чего нет и не может быть в базе: какой диалог открыт,
выбранная вкладка и получас, несохранённый ввод, перетаскивание между
`dragstart` и `drop`, «команда в полёте». Всё остальное — на сервере.

⛔ **`hold` — это НЕ «диалог открыт».** Скопировать `busy()` из `panel.js`
буквально нельзя: там замирает вся страница на любом открытом `<dialog>`, и
рабочее место с забытой открытой карточкой перестаёт узнавать о бронях со
второго места, оставаясь живым НА ВИД. На старой странице это прикрывала
перезагрузка по 303 после действия; у React её нет.

⭐ **Уточнение Олега 19.09, и оно сильнее первой редакции:** `hold` — это
состояние КОНКРЕТНОГО интерактивного ресурса, а не заморозка страницы. Не

```
диалог открыт → экран замер
```

а

```
диалог открыт → опрос идёт → состояние применяется → диалог сверяется с ним
```

Иначе React-панель превратится в тот же `panel.js`, где открытая форма
фактически замораживала весь экран. Поэтому `hold` у ХУКА держит только то,
чему применение навредит прямо сейчас и ненадолго:

```
hold() = идёт перетаскивание          (данные увезли бы блок из-под мыши)
      || команда в полёте             (ответ всё равно на подходе)
```

а **грязный черновик держит СЕБЯ, а не экран**: диалог не пересевает поле,
пока его правят, — и канва под ним продолжает жить.

⚠️ `hold` обязан быть ПРЕДИКАТОМ над рефами, а не булевым пропом: проп доезжает
до хука пассивным эффектом, то есть кадром позже. Для перетаскивания неважно,
для команды длиной в круг по 127.0.0.1 — ровно та щель, ради которой защита и
ставится.

Черновик засевается ОДИН раз и только из полного `comment` (никогда из
`comment_cut`); пока он чист — приехавшие данные пересевают его; стал грязным —
поле остаётся, остальной экран обновляется.
⛔ Версии комментария в C26.5.3 не заводится: два человека, правящие один
комментарий в одну минуту, по-прежнему теряют одну правку — ровно как сегодня
на легаси-странице. Названо и принято, не регресс.

**Запись исчезла, пока диалог открыт** (отмена со второго места, перенос на
другой день): молча размонтировать нельзя — человек решит, что промахнулся
мимо кнопки. Диалог остаётся на НАДГРОБИИ (последний блок, из которого он был
отрисован), показывает серверную плашку и все кнопки отключает. Из надгробия
нельзя ничего отправить: им можно только сказать «этого больше нет».

## 3. Команды: ответ действия НЕ несёт состояния

```
click → command → server mutation → canonical live state → refresh() → apply
```

Пять существующих маршрутов получают в строке запроса `screen=panel`, и `_done`
при `screen == "panel"` возвращает ответ БЕЗ `data` — ни на удаче, ни на
отказе. Ни одного нового маршрута и ни одной новой функции правил: правила
остаются одни на страницу и на API.

⛔ Почему не «пусть панель зовёт те же маршруты как есть»: `_done` на удаче
строит модель ДНЯ, у которой ДРУГОЙ ключ колонки. Подмена одной модели другой
запрещена разбором C26.1 и стреляет у клиники, пережившей переименование
врача: визит исчезает, час выглядит свободным, в него записывают второго.
⛔ Почему не «пусть команда отвечает конвертом»: тогда `X-DP-Hash` надо не
забыть в шести местах, а клиенту нужна вторая дверь в хук. В раскладке «без
состояния» забывать нечего.

Хук получает наружу ровно одно новое — `refresh()`: немедленный тик, отпечаток
НЕ трогает. ⛔ `applyLive`/`applyData`/`setData` не заводить, и ⛔ `DashModel`
не поднимать в собственный `useState`: этот обход компилируется, проходит
typecheck, lint и `npm test`, работает на демо-профиле и ломается только у
клиники с двумя рабочими местами.

Три вещи против гонок, все обязательны:

1. **Порядковый номер тика.** ⭐ Он защищает СВЕЖЕСТЬ СОСТОЯНИЯ, а не порядок
   доставки (формулировка Олега 19.09): `номер ≤ применённого → выбросить`,
   `номер > применённого → применить`. Лечит случай «`200` с ДОкомандным
   состоянием, доставленный ПОСЛЕ команды», от которого `hold` не спасает —
   команда уже завершилась. Без этого визит исчезает с канвы на 12 секунд, и
   регистратура записывает второй раз.
   ⚠️ Порядок проверяется ТОЛЬКО у `apply`: «сессия кончилась», «чужая
   поверхность» и «непонятный ответ» верны независимо от того, кто кого обогнал.
   ✅ Сделано и доказано снятием сторожа: без него проверка краснеет ровно тем,
   чем должна, — старое состояние ложится поверх свежего.
2. `hold()` истинен, пока команда в полёте, и ставится синхронно, до `fetch`.
3. `refresh()` зовётся на ЛЮБОМ исходе, включая 409 и 422. ⛔ Особенно на 409:
   он означает «каноническое состояние уже изменилось под тобой», а отказ
   приходит без данных — человек прочтёт «интервал занят» и будет смотреть на
   пустую ячейку.

Конверт дополняется четырьмя ключами: `actions`, `note_actions`, `note_ends`,
`slotform` (`{services, birth_max}`). ⭐ В конверт, а не вторым каналом: они
постоянны, значит отпечаток не двигают НИКОГДА, инвариант цел, а второй канал
— это второе место, где можно забыть. ⚠️ Имя `slotform`, а не `form`: ключ
`form` с меньшим числом полей, чем `form` модели дня, — ловушка для следующего.
⛔ `birth_max` считать от `datetime.now(eng.TZ)`, не от `date.today()`: иначе
поле переворачивало бы отпечаток в полночь по часам машины.

⛔ Своих проверок занятости на клиенте НЕ добавлять: сериализация уже есть
(`_slot_lock`, один критический участок на «проверка + вставка»). `clash` —
подсказка, и не имеет права не пустить команду. Ключ идемпотентности не нужен:
второй клик даёт честный `dup`; нужна только блокировка кнопки до ответа.

⭐ Критерий Олега в проверяемом виде: **после команды у A и у B состояние
приезжает ОДНИМ И ТЕМ ЖЕ путём.** Не «оба в итоге сойдутся», а «второго пути
нет».

## 4. Граница владения с `panel.js`

> **После переезда поверхности на React ни одна строка `panel.js` не читает и
> не пишет узел, который печатает React: экранная область скрипта на
> React-странице не заводится вовсе.**

Скрипт разрезается на две области — перестановка `})();` и один `if`, а не
рефакторинг. **Каркасная** (остаётся всегда): Ctrl+K, `togglePhone`,
`pickName`, часы сайдбара, `dp_pos`, плашка. Признак каркасного куска
механический: он ищет узел по `id`, который печатает `core/layout.py`, и не
ищет ничего по классу расписания. **Экранная** (не регистрируется при
`DP_REACT`): живой опрос, прокрутка агенды, перетаскивание, счётчик KPI,
`markFresh`, `placeNowline`, `paintWaits`.

⛔ `var DP_REACT` переезжает в НАЧАЛО файла: сегодня он ниже пяти из
четырнадцати кусков, и охрана внутри них прочитала бы `undefined` (`var`
поднимается, значение — нет) — выглядела бы написанной и не работала.
⛔ Охрана ставится вокруг РЕГИСТРАЦИИ, а не внутри функции: интервалы и
слушатели заводятся на React-панели всё равно, и первая строка, добавленная
перед `return`, оживит мутацию React-поддерева в месте, которое выглядит
невинно.

⚠️ Перетаскивание сегодня молчит ПО СЛУЧАЙНОСТИ (нет `#movedlg`, нет
`data-mv`). Шаг `f` обе случайности снимает: React-овский диалог переноса — без
`id`, и это записанное решение, а не совпадение. Прокрутка агенды — постоянный
capture-делегат, который СРАБАТЫВАЕТ на React-овской `.ag-l`; мутаций нет,
сцена его не увидит, след всплывает чужой позицией списка после `?ui=legacy`.

✅ **Одно исправлено сразу, в C26.5.2, не дожидаясь `f`:** класс `anim` на
`<html>` ставит каркас всякой странице, а снимало его ЕДИНСТВЕННОЕ место —
`apply()` живого опроса, который на React-странице не запускается. `.anim
.ag-i`, `.anim .spark` и `.anim .statbar>div` переигрывали бы вход на каждом
новом узле вечно. Снимает теперь `DashScreen` — на ПЕРВОМ ОБНОВЛЕНИИ, а не на
первой отрисовке: у легаси первая отрисовка серверная и анимируется, а класс
снимает первый же `apply`, то есть первое изменение.
⚠️ Сцена этого не поймала бы: анимация CSS мутацией DOM не является.

Перед `a` — полшага, которого в списке нет.

| **d** | заметка | ⛔ только «Șterge»: правки текста нет ни на одном экране, и серверного правила для неё не существует — изобретать его в шаге миграции запрещено | «у заметки ровно одна кнопка»; «`part_note` приезжает кодом» |
| **e** | запись по клику | `nophone` — намерение ИЗ ФОРМЫ, а не «телефон пустой» (08-16) | «кнопка заперта до ответа»; «на 409 диалог не закрывается и зовётся `refresh()`» |

Новые правила раскладки (каждое = проверка в `test_structure.py` + строка в
`mutate.py`): «легаси-скрипт не называет узел, который печатает React» (список
имён собирается ИЗ КЛИЕНТА, поэтому новый React-класс, который `panel.js` уже
трогает, покраснеет без единой правки `panel.js`) и «маршрут команды не
возвращает состояния живой поверхности».
⚠️ Ограничение первой мутации назвать письменно: `mutate.py` копирует только
`bot/`, `frontend/` берётся из настоящего дерева, поэтому мутанта «React вырос»
этой машиной не изобразить.

## 6. ⛔ Чего в C26.5.3 НЕ делать

1. Не поднимать `DashModel` в `useState`, не заводить `applyLive`. Одна дверь.
2. Не возвращать состояние из команд — ни моделью дня, ни конвертом.
3. Не класть `cards` в конверт панели и не строить второй источник карточки.
4. Не заводить двойник `POST /admin/relink`: он живёт настоящей формой с 303,
   делается раз за жизнь установки, и перезагрузка после него законна.
   ⚠️ Если когда-нибудь заводить — `api_require(PERM_DOCTORS)`, а не
   `api_guard`: скопированная охрана отдала бы регистратуре право переклеивать
   чужую историю, и видно это только по летописи.
5. Не править заметку текстом.
6. Не «чинить по дороге» расхождение `_add_note` → `bad` против `_add_appt` →
   `bad_off` для выключенного врача. Оно старое и пиннутое, выглядит опечаткой
   ровно настолько, чтобы его поправили заодно, — а регистратура увидит другое
   слово на том же действии.
7. Не трогать списки с включающей полярностью в этом шаге.
8. ⚠️ Не возвращать `markFresh` и счётчик KPI здесь — но это **названные
   потери**, а не уборка, и с 19.09 они не в бэклоге, а в **рубеже выката**
   (слово Олега): переход, завершённый без подсветки приехавшей записи, — это
   потеря поведения рабочего процесса, а не визуальная разница. Подсветка и
   есть то событие, ради которого журнал висит открытым на стойке.
   ➡️ Отдельная ступень **C26.5.4 «возврат утраченного паритета»**:
   `markFresh` + оживление цифр. ⛔ `schedule_dash` не включается у клиники,
   пока она не закрыта.
9. Не включать `schedule_dash` у пилота, пока не закрыт `g`.
10. Не читать день из `location.search`: плашка переписывает адрес, и разница
    появится только при заходе с `?msg=…`, то есть после любого действия.
