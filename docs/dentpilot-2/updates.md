# Обновления

## ⭐ Порядок с 03.10 (слово Олега «вот этим и займемся»)

Вопрос «как доставлять обновление, когда программа станет папкой (Tauri)» решён
так: **сервер обновлений → обновление установщиком → оболочка Tauri.** Первые
два шага полезны и без Tauri.

1. ✅ **Сервер обновлений** (03.10). Программа сначала спрашивает
   `cloud.dentpilot.md/v1/update?channel=…&current=…` (`cloud/app/updates.py`):
   сервер сам ходит в GitHub не чаще раза в 5 минут на канал и отвечает версией,
   страницей и файлами (ссылка, размер, sha256 — те, что отдал GitHub). Провод
   программы — `bot/app/update_server.py`, без импортов проекта: облачный прогон
   грузит его по пути и ходит в живой сервер (договор двух сторон).
   ⛔ Ответ не принимается на веру: ссылка — только на выпуск НАШЕГО репозитория с
   тем же тегом и точным именем файла, sha256 — 64 знака, размер — разумный,
   версия — новее стоящей. Сервер может назвать один из настоящих выпусков, но не
   подсунуть файл и не откатить программу. Сам файл качается с GitHub, как раньше.
   ⛔ Сервер — не условие: молчит или ответ не прошёл проверку — прежние пути к
   GitHub ниже без изменений. Черновики (токен разработчика) — мимо сервера.
   ⛔ Канал называет программа; назначать канал с сервера (`beta` компьютеру из
   админки) — это «сервер командует программой», за границей plan-fleet-admin;
   только по слову Олега.
   ⭐ Харнесс держит `DENTART_UPDATE_CHECK=off`: 300 тестовых серверов за прогон
   спрашивали GitHub при каждом старте и выедали анонимную квоту 60 в час — у
   канарейки на той же машине проверка шла запасным путём (02.10: 0 из 60).
2. ✅ (03.10) — **Обновление установщиком.** Канарейка — с 1.37.0, клиники — с 1.37.3.
   Сделано: `bot/app/authenticode.py` (WinVerifyTrust и версия файла через
   `wintrust`/`version.dll`, без оболочек), операция `install-setup` в
   `privileged.py` (копия → sha256/размер → подпись из `SIGNERS` → версия новее →
   «started» → установщик отдельно), `update._update_by_setup` (zip выпуска →
   ровно один установщик ожидаемого имени → подпись проверяется ещё ДО окна UAC →
   задача-сторож → окно UAC → выход по «started»), установщик пишет итог в
   `/RESULT=` (`ok` в `ssDone`, `fail` в `DeinitializeSetup`). ✅ **Включено всем
   с 1.37.3** (`installer_mode` канал больше не спрашивает). До того — только
   канарейке: тихую установку из-под UAC прогон не исполняет, и клиникам путь
   включили после двух её живых проходов. ⚠️ Путь выбирает СТОЯЩАЯ версия:
   на 1.37.3 клиники приезжают ещё подменой exe, установщиком — со следующего
   выпуска. Рычаг назад — `DENTART_UPDATE_VIA=exe` (снят 22.10.2026 вместе с подменой exe).
   Файл обновления — подписанный
   `DentPilot-Setup-X.Y.Z` из того же выпуска; ставит его привилегированная
   операция за UAC в тихом режиме. Это нарушает главный инвариант `privileged.py`
   («за повышением ничего не исполняется»), поэтому закрывается подписью кода, а
   не обходится: исполнитель сам копирует установщик в папку только для
   администраторов, сверяет sha256 и подпись Authenticode с НАШИМ сертификатом и
   версию файла (не старее стоящей), и только потом запускает. Установщик
   сохраняет данные, обновляет запись «Программ и компонентов» (сегодня она
   отстаёт) и перезапускает программу обычным пользователем; прежний установщик
   остаётся для отката. Нынешние программы умеют только подменять один exe,
   поэтому переход — в два выпуска: сначала программа учится ставить установщик,
   следующим выпуском этим путём приезжает Tauri.
   ⚠️ **Перезапуск — заранее и обычным пользователем.** Тихий установщик сам
   закрывает работающую программу (`CloseApplications=yes`) — вместе с процессом,
   который ждёт итога и должен перезапустить. Запуск из-под установщика тоже
   нельзя: `runasoriginaluser` у уже повышенного родителя не к кому вернуть, и
   при входе в UAC ДРУГОЙ учёткой администратора программа поднялась бы под ней —
   `db.key` завернулся бы под чужой DPAPI. Поэтому ДО запроса прав программа
   заводит задачу планировщика от своего пользователя (как `restart_app`): та

   исполнитель отметил «начал», — окно подтверждения закрытия иначе держало бы

## Оболочка Tauri: обновление и сторож (Т10, 18.10.2026)

Программа под оболочкой — ПАПКА: `{app}\DentPilot.exe` (оболочка, Rust) +
`{app}\engine\DentPilot-Engine.exe` (движок, PyInstaller папкой). Контракт —
[tauri-contract.md](tauri-contract.md) § 1–2, слово `quit`. Обновляет её только
установщик (шаг 2 выше); разведка, доставка, проверки — прежние. Что другое:

```
движок: «Actualizează acum» → zip выпуска → размер+sha256 → один DentPilot-Setup-X.Y.Z.exe
   → подпись SIGNERS (до окна UAC) → install.request
→ сторож: КОПИЯ оболочки <данные>\updates\DentPilot-watch.exe, задачей планировщика
   (вне «задания» оболочки), `--watch …` — аргументы `restartwatch.argv_for`;
   метка .run — «пошёл»; на экране заставка «Se instalează actualizarea… v1.46.1 › 1.47.0»
→ окно UAC: ShellExecute runas engine\DentPilot-Engine.exe --privileged install-setup
   (процесс создаёт служба UAC «от имени» движка — и он В ЗАДАНИИ оболочки, см. ниже)
     за UAC: корень = папка оболочки (лаунчер, BASE по имени exe) → копия мастера
     {app}\updates\DentPilot-Setup.exe → sha256, подпись, версия новее {app}\DentPilot.exe
     → мастер отдельно, CREATE_BREAKAWAY_FROM_JOB (вон из задания) → «started» последним
→ движок видит «started» → sidecar.request_quit("update") → оболочка выходит без вопроса,
   шлёт stop → движок останавливает сервер, ЗАКРЫВАЕТ базу, выход 0
→ тихий мастер ждёт выхода обоих exe (Т9, до 30 с) → меняет {app}\DentPilot.exe и
   {app}\engine\… → /RESULT= «ok»
→ сторож: итог → ждёт выхода старой оболочки → запускает {app}\DentPilot.exe → снимает задачу
   («started», а мастера нет 20 с — не ждёт 9 минут: «nu s-a instalat», прежняя программа)
```

### ⛔ Живой проход 2.0.0 → 2.0.1 встал (18.10, 21:38) — задание оболочки

У Олега: `install.result` = «started» (21:38:19), `setup.log` нет, процесса
мастера нет; оболочка и движок вышли честно («обновление установщиком пошло»
→ «оболочка попрошена закрыться» → «остановка по слову оболочки», код 0),
сторож ждёт. Мастер не стартовал вовсе.

**Причина — подтверждена опытом** (`tests/jobstand.py`, без окна UAC).
Повышенный процесс служба UAC создаёт с атрибутом
`PROC_THREAD_ATTRIBUTE_PARENT_PROCESS` = вызывающий (движок), а с ним
процесс наследует у родителя и «задание» (так сказано у
`UpdateProcThreadAttribute`: «…the process token, and job object»). У
оболочки задание — KILL_ON_JOB_CLOSE без права выхода. 2.0.0/2.0.1 писали
«started» и СПАЛИ 3 с до запуска мастера; по «started» оболочка закрылась,
Windows погасила задание — и операцию за UAC во сне. Т10 считал «runas — вне
задания» и проверить этого без человека у окна UAC не мог.
Опыт (18.10, Windows 11, задание как у оболочки, процесс «за UAC» атрибутом
родителя от процесса в задании): он в задании — да; прежний порядок
(«started» → 3 с → запуск) — мастера нет, итог «started», журнала нет (ровно
живой проход); запуск без сна, но без выхода из задания — мастер погашен
вместе с заданием; `CREATE_BREAKAWAY_FROM_JOB` при задании без
`BREAKAWAY_OK` — отказ Windows (WinError 5); с `BREAKAWAY_OK` — мастер жив и
пишет «ok».

**Починка (2.0.2):**
- оболочка: задание `KILL_ON_JOB_CLOSE | BREAKAWAY_OK` (`engine.rs::JOB_LIMITS`)
  — выйти может только ПОПРОСИВШИЙ. ⛔ Не `SILENT_BREAKAWAY_OK`: тогда молча
  выходили бы все дети, первым — интерпретатор venv в разработке (ребёнок
  пускача), и движок пережил бы оболочку. Опыт: с `BREAKAWAY_OK` дети и
  внуки, которые не просят, остаются в задании (и внуки dev-движка через
  «тихое» задание пускача venv — тоже) и гибнут с ним;
- за UAC: мастер — `CREATE_BREAKAWAY_FROM_JOB`, и «started» — ПОСЛЕДНИМ, после
  запуска (`privileged._install_setup`): всё, что стоит после «started», может
  не исполниться. Сна нет — ждать выхода программы умеет мастер (Т9). Мастер
  успел написать итог раньше «started» — его слово главнее (запись «started»
  только в новый файл). Не запустился — отказ СЛОВАМИ, не «fail»: программа ещё
  жива и сама скажет сторожу «cancelled»;
- сторож (`watch.rs::SetupWatch`): «started» стоит, а процесса
  `DentPilot-Setup.exe`/`.tmp` нет 20 с подряд — «Actualizarea nu s-a
  instalat — se pornește versiunea curentă…» и прежняя программа сразу, а не
  через 9 минут пустой заставки. (Python-сторож окна pywebview этого не умел;
  снят 22.10.2026 вместе с окном.)

Куда «выходит» мастер: из задания оболочки — вверх по цепочке, пока задание
разрешает. Оболочка, поднятая сторожем, сидит в задании ПЛАНИРОВЩИКА (опыт:
у процесса задачи пределы 0x0 — ни гашения, ни выхода); мастер остаётся в
нём, и оно его не гасит (Т10: оболочка, поднятая сторожем, пережила и выход
сторожа, и снятие задачи).

Остальные пути, которые должны пережить оболочку: сторож обновления и
перезапуска — задача планировщика (вне задания по построению);
`uninstall-version`, `auth-reset` и правило брандмауэра (`lan.py`, `cmd.exe`
за UAC) — тоже в задании, но оболочку не закрывают и кончаются за доли
секунды. Документ фиши, открытый программой Windows, до 2.0.3 сидел в
задании и гас вместе с DentPilot; с 2.0.3 его открывает
`core/shellopen.open_file` вне задания ([sidecar.md](sidecar.md) ›
«Ловушка задания»).

**Стенд без UAC** — `test_privileged.suite_setup_outlives_shell`
(`.\dev test P4`): задание с пределами, прочитанными из строки `JOB_LIMITS`
в `engine.rs`, «движок» в нём, процесс «за UAC» атрибутом родителя,
настоящий `install-setup` из исходников и настоящий `_spawn_setup` с
подставным мастером (пускач distlib + `#!python` + zip; подпись и версия —

## Как это было устроено до установщика (снимок 20.09)

⚠️ История: с 03.10 ставит установщик (шаг 2 выше), подмена exe (bat,
`.old.exe`, ассет `DentPilot.exe`) снята 22.10.2026. Разведка и доверие к
источнику — прежние.

У обновления **два слоя**, и к GitHub привязан только первый:

```
разведка: какая версия свежая, где файл   ← знает про GitHub
   ↓
доставка: urlopen(asset_url) → файл        ← источник ЛЮБОЙ
```

| Вопрос | Ответ |
|---|---|
| Откуда узнаёт о версии | четыре источника: `/releases/latest`, GraphQL, список релизов и **веб-путь без API** через `releases.atom` |
| Что скачивает | ассет с именем **точно** `dentpilot.exe` |
| Контрольная сумма | **да** — sha256 из поля `digest`, плюс точный размер, плюс порог 5 МБ |
| Цифровая подпись | **нет никакой** |
| Как ставит | установщик не запускается: bat уводит рабочий exe в `.old.exe`, новый кладёт на его место |
| Перезапуск | через планировщик задач |
| Откат | `.old.exe` рядом, удаляется только после того, как база **открылась** |
| Проверка | при старте и каждые 6 часов |

⭐ **Имя ассета сравнивается точно, и это не педантизм.** GitHub сортирует
ассеты по имени, и `DentPilot-Setup-*.exe` встаёт **раньше** `DentPilot.exe`
(`-` = 0x2D меньше `.` = 0x2E). Отбор «первый .exe в списке» скачал бы
**установщик** и затёр им работающую программу.

⭐ **Ноль от планировщика — не доказательство запуска.** Скрипт первой строкой
создаёт файл-метку, программа ждёт её до 10 секунд и только тогда гасится. Не
дождавшись — удаляет задачу и остаётся жить.

⭐ **Веб-путь без API существует не для красоты.** Анонимный лимит GitHub — 60
запросов в час **на адрес**, а клиника сидит за NAT провайдера и делит адрес с
чужими программами. Проверено живьём: API ответил 403 rate limit, программа
ушла на `releases.atom`, определила версию и не сломалась.

## Почему не обновлятор Tauri

⛔ **Он закрывает путь назад.** Его модель — «скачать и запустить инсталлятор»,
а не «подменить файл». После первой такой установки клиент принимает только
подписанные артефакты штатного формата и не примет PyInstaller-сборку. А
правило проекта запрещает снимать релиз и перевешивать `latest` — значит чинить
плохую сборку можно только следующей сборкой того же стека.

⛔ **Он требует вечный приватный ключ.** Публичный ключ вкомпилирован в
установленный бинарник; переподписать его удалённо нечем, потому что
единственный канал доставки — тот самый обновлятор, который теперь отвергает
неподписанное. Потеря ключа = обновления умирают у **всех** клиник молча,
починка выездом на каждую машину.

⛔ **Он не умеет каналов.** `stable` / `beta` / `draft` воспроизводятся частично
и ценой костылей.

## ⭐ Почему переход на Tauri достаётся почти бесплатно

⛔ **Устарело 18.10 (Т10), не исполнять.** Раздел писался, когда Tauri виделся
одним exe. Программа под оболочкой — папка (`DentPilot.exe` + `engine\`), и
одиночный `DentPilot.exe` в выпуске стал бы для старых программ с подменой exe
оболочкой без движка — мёртвой программой. Переход — установщиком (раздел
«Оболочка Tauri» выше). Ниже — история рассуждения.

Нынешний обновлятор **бандлер-агностичен**: он не проверяет, что скачанный файл
— PyInstaller-сборка. Он проверяет имя, размер и sha256, после чего подменяет
файл.

Значит Tauri-сборка с тем же именем `DentPilot.exe`, читающая данные из своей
же папки, приедет установленным клиникам **старым механизмом** — без
переходного релиза и без единой новой строки на их стороне.

⚠️ Проверять **экспериментом**, а не предположением:

```
собрать заготовку Tauri
      ↓
назвать DentPilot.exe
      ↓
положить вместо dist\DentPilot.exe
      ↓
выполнить существующий путь обновления
      ↓
проверить: запуск, FastAPI, порт, база, данные клиники, файлы
```

Только после успеха трогать релизные скрипты.

⛔ **У своего адреса есть цена.** Сегодня доверие держится на HTTPS до
github.com плюс sha256, который считает GitHub. Свой хост делает якорем доверия
**вас**: кто получил доступ к серверу, тот разослал произвольный exe во все
клиники одним движением. Без подписи кода это ослабление, а не усиление.

## Что остаётся неизменным при любом канале

Имя-размер-sha256, подпись установщика нашим сертификатом, доказательство
запуска сторожа файлом-меткой, и правило **релизы только вперёд**.

## Чего проверка не покрывает

⚠️ `POST /admin/update/run` — спусковой крючок самообновления — **не покрыт ни
одним тестом**. Это дыра сегодняшнего продукта, не последствие миграции.

⚠️ Обновление на ноутбуке **от батареи** не проверял никто: у задачи
планировщика `DisallowStartIfOnBatteries` включён по умолчанию, и снять его
ключом нельзя. Проверяется только запуском на настоящем ноутбуке без питания.

⚠️ Пропущенные выпуски опасны не обновлятором, а схемой базы: клиника на
`stable` всегда прыгает на самую свежую версию, а миграции односторонние и
идут по шагам. Прогонять новый клиент на всех базах-образцах из
`test_migrate.py`.
