# Как выпускать версию

Фичи пишутся как обычно. Отличается только момент выпуска.

⭐ **С Tauri (Т9, 18.10.2026) программа — ДВЕ части**, и подменой одного файла
её не обновить (контракт — `docs/dentpilot-2/tauri-contract.md` § 1):

```
C:\Program Files\DentPilot\
  DentPilot.exe                  оболочка Tauri: окно, значок у часов, уведомления
  engine\DentPilot-Engine.exe    движок (PyInstaller папкой): сервер, база, копии
```

Поэтому и новая клиника, и обновление идут **одним путём — мастером установки**:

| Артефакт | Кто его берёт | Имя |
|---|---|---|
| папка программы | никто снаружи: её пакует мастер, её гоняет стенд сборки | `dist\DentPilot\` |
| мастер установки | **новые** клиники: USB, прямая передача | `DentPilot-Setup-X.Y.Z.exe` |
| он же в zip | **обновление** у установленных клиник и страница релиза — ЕДИНСТВЕННЫЙ ассет выпуска | `DentPilot-Setup-X.Y.Z.zip` |

Отдельный `DentPilot.exe` в выпуск больше не кладётся: это оболочка без
движка, обновиться ею нельзя.

## Три правила, которые нельзя нарушать

**1. В релизе ровно один файл — `DentPilot-Setup-X.Y.Z.zip`, и ни одного `.exe`.**
Клиника старой сборки выбирала ассет `.exe` из списка по имени, и `.exe` рядом
— это файл, который она может скачать вместо программы и затереть им себя.
Поэтому мастер уезжает в релиз **архивом**. Это правило постоянное: клиника,
которая пропустила обновление и включит компьютер через полгода, всё ещё
выбирает по-старому. Держат `release.py` (не зальёт и не опубликует иначе) и
`check_release.py`.

**2. Имя `DentPilot-Setup-X.Y.Z.zip` — не косметика.** Версия в имени = тег:
обновление находит архив по шаблону имени, сверяет версию с тегом, а внутри
ждёт ровно один `DentPilot-Setup-X.Y.Z.exe`, подписанный НАШИМ сертификатом
(`update._update_by_setup` → `privileged`). Не то имя или чужая подпись — и
все клиники встанут на «версия объявлена, обновиться нечем».

**3. Релизы только вперёд.** Не удалять, не снимать с публикации, не
перевешивать метку «latest» на старый релиз. Клиника, которая уже обновилась,
сравнивает свою версию с тегом строго на «больше» — после отката тега она
больше никогда ничего не получит. Плохая сборка чинится **выпуском следующей**.

## Порядок

```bash
# 1. фича закончена и закоммичена (вместе с installer/ и скриптами сборки)
git status --porcelain     # должно быть пусто

# 2. поднять APP_VERSION в bot/app/engine.py — строго три числа X.Y.Z
#    и закоммитить. Остальные потребители версии (package.json, свойства
#    exe) подтягиваются сами: sync_version.py зовёт сборка, а .\dev check
#    и прогон краснеют, если номера разошлись.

# 2b. стенды в живом Edge — переходы, сдвиги первого кадра, ожидание, F5,
#     монтаж, права (25.09: то, что видит канарейка, а прогон не видит)
.\dev bench

# 3. собрать и проверить (сборка сама откажется на грязном дереве)
#    СНАЧАЛА войти в SimplySign Desktop: выпускная сборка подписывает оболочку,
#    движок, мастер и деинсталлятор и БЕЗ подписи не идёт (нет отпечатка или
#    ключ недоступен — стоп). Последние строки вывода — «podpis …» у трёх
#    файлов. Нужны: Rust на D:\Rust (оболочка), .venv-desktop, npm, Inno Setup.
#    Время: движок ~3,5 мин, оболочка — 4,5 мин с нуля / ~2 мин повторно,
#    стенд пары 12 с, мастер ~1 мин. (docs/dentpilot-2/installer.md › «Сборка»)
powershell -File Build-Installer.ps1
#    Пробная сборка для себя (без SimplySign, можно грязное дерево):
#    powershell -File Build-Installer.ps1 -NoSign
#    ⛔ Она не для выпуска: в releases\ не кладётся, а release.py prerelease
#    проверяет подпись мастера сам и неподписанный не зальёт.

# 3a. ТОЛЬКО если правка тронула миграции (bot/app/db.py: MIGRATIONS_*,
#     SCHEMA_VERSION, слотовые индексы) — канарейка на СОБРАННОМ бинарнике:
python scripts/check_slot_guard.py

# 4. только теперь тег — на тот коммит, из которого собрано.
#    ⛔ Тег отправлять ПОИМЁННО, а не «--tags»: у репозитория лежат старые
#    локальные теги БЕЗ «v» (наследство веб-формы, 08-06), и «--tags» утаскивает
#    их на origin заодно — 08-17 так уехал 1.13.0, указывающий на другой коммит,
#    чем v1.13.0. Релиза на таком теге нет, поэтому клиникам он не виден, но в
#    списке тегов он и есть та самая ловушка «тег без v».
git tag -a v1.11.0 -F <файл-с-описанием>
git push origin main && git push origin v1.11.0

# 5. pre-release с ОДНИМ ассетом (zip мастера) — скриптом, НЕ веб-формой.
#    Перед заливкой скрипт проверяет мастер тем же, чем его проверит программа
#    клиники: один exe с именем версии в zip, наша подпись, версия файла.
python scripts/release.py prerelease 1.11.0

# 6. канарейка: своя машина (beta) обновляется, поработать в ней руками

# 7. хорошо -> опубликовать (снимает метку, ставит latest)
python scripts/release.py publish 1.11.0

# 8. проверить опубликованное глазами клиники
python scripts/release.py check 1.11.0

# 9. демо на сайте (demo.dentpilot.md) — на ту же версию, что получили клиники
#    (3–4 мин сборки на сервере, ~30 с без демо; копии посетителей сбрасываются)
ssh deploy@13.140.191.129 '~/dentpilot-demo/src/demo/update.sh v1.11.0'
curl -s https://demo.dentpilot.md/demo/health # version = 1.11.0, ready = slots
#    ⛔ Только /demo/health: его отвечает сам шлюз, слота он не берёт. До 07.10
#    шлюз давал слот на час любому запросу без куки, и проверка `…/health`
#    занимала одну из шести копий демо на каждый выпуск.
```

⛔ **Веб-формой релизы не трогать вообще.** За два дня она дала три разные
ловушки: «create tag on publish» завёл тег без «v» на чужом коммите со
старыми ассетами; правка молча не сохранялась без нажатия «Update release»;
Publish существующего релиза создавал черновик-двойник с тем же тегом, и
latest не двигался. `scripts/release.py` работает с релизом по id через API,
двойников не создаёт и откажется публиковать узел с неправильными ассетами.
Токен берёт сам: из окружения, из git credential (тот же, что пушит) или из
dental.env. Команда `status` показывает все релизы с флагами — двойники и
черновики видны сразу.

Шаг 3 идёт **до** тега намеренно: тег — это утверждение о коде, который
действительно собрался и запустился, а не о коде, который мы собирались собрать.

⛔ **Релиз, который трогает миграции, не публикуется без шага 3a.** Правило
написано опытом: 1.20.0 ужесточала уникальный индекс, и у клиники с двумя
рабочими местами `CREATE UNIQUE INDEX` падал — программа переставала
открываться, навсегда. Риск был назван в ревью и всё равно уехал клиентам,
потому что никто не собрал ту самую базу и не запустил. `scripts/check_slot_guard.py`
собирает её сам: делает КОПИЮ живой базы (⛔ боевая только читается), приводит
её к состоянию клиники до обновления, вносит двойную бронь и запускает
**собранный exe** — программа обязана стартовать, оставить прежнюю защиту,
назвать директору конфликтные часы, а после разведения поднять полную защиту
сама. Третий шаг скрипта отдельно проверяет базу, пришедшую от 1.20.0: два
индекса широких, третьего нет — обновление не имеет права их СУЗИТЬ.
⚠️ Этого не видит ни `.\dev test` (он про исходники), ни `smoke_exe.py` (он про
то, открываются ли страницы). Ключ `--db` — если живой базы под рукой нет:
`python scripts/check_slot_guard.py --db путь\к\копии.db`. Зашифрованную базу
скрипт откроет отказом и скажет почему: конфликт в неё мимо программы не внести.

Файл на шаге 5 — **поимённо** (так делает `release.py`). Никакого
`dist/*.exe`: в `dist` лежит мастер установки, и в релизе он стал бы `.exe` —
ровно то, что запрещает правило 1.

## Что проверяет сборка (и почему)

Порядок внутри: клиент (vite) и движок папкой (`Build-Engine.ps1`, внутри —
стенд протокола `engine_check.py --exe`, 39 проверок) → оболочка
(`cargo build --release --locked`) → папка программы `dist\DentPilot` →
подпись оболочки и движка → стенд пары `scripts/shell_check.py` → Inno
(подписывает мастер и деинсталлятор) → zip.

`Build-Installer.ps1` откажется работать, если:

- **дерево грязное** или **коммиты не запушены** (выпускная) — иначе тег не
  воспроизводит бинарник, а недоделанная работа из соседнего окна уезжает всем
  клиникам в один клик;
- **нет отпечатка сертификата или подпись не удалась** (выпускная) — до Т9
  сборка шла дальше одной жёлтой строкой «BEZ PODPISI»;
- **`APP_VERSION` не вида X.Y.Z** — тег `v1.10` даёт `(1, 10)`, что меньше
  `(1, 10, 0)`, и релиз становится невидимым сразу для всех;
- **собранный движок не говорит по контракту** (`engine_check.py`): трубы DP1,
  остановка словом и закрытым stdin, второй экземпляр, чужой порт, страницы;
- **собранная пара не проходит стенд** (`shell_check.py`, 22 проверки):
  оболочка из временной «установки» (`--tray`) находит движок в `engine\`,
  `/health` отвечает, странице выдан `dpShell` v1, обход страниц свежей
  установки (`smoke_exe wall`) и живой картотеки (`grace`), второй запуск
  уходит сам, честный выход через вопрос оболочки (код 0, движок остановлен
  словом, порт свободен, `-wal` сброшен), снятие оболочки гасит движок.
  ⚠️ На шаге выхода на секунду появляется окно «Închideți DentPilot
  complet?» — стенд сам нажимает «Да» по PID своей оболочки;
- **версии разошлись**: `/health`, свойства `DentPilot.exe`, свойства
  движка, `dpShell.version` и `engine.py` обязаны совпасть;
- **в мастере не всё или лишнее** — состав сверяется по журналу ISCC
  (`dist\iscc.log`, строки `Compressing:`) с папкой программы, без запуска
  мастера;
- **мастер не подписан** (выпускная).

Готовый мастер установки сборка сама кладёт в `D:\DentProject\releases` — это то,
что отдают клинике (папка задаётся ключом `-SetupDir`, пустая строка отключает).
На верхнем уровне там всегда ровно один установщик: прошлые версии уезжают в
`arhiva\`, а не удаляются — сборка не должна тихо уничтожать то, что уже кому-то
отдано. `dist` при этом остаётся выходом сборки и перезаписывается каждым билдом.

Имя артефакта берётся из того, что **exe сам о себе говорит**, а не из
`engine.py`. Назвать сборку чужой версией больше нельзя — это уже случалось:
`DentPilot-Setup-1.10.0.exe` содержал 1.9.1.

`scripts/check_release.py` проверяет уже опубликованный релиз тем же правилом
сравнения версий, что и программа: draft/pre-release, формат тега, ровно один
ассет `DentPilot-Setup-X.Y.Z.zip` той же версии, что тег, ни одного `.exe`,
состояние и размер ассета.

⚠️ **Чего сборка НЕ проверяет — саму установку.** Мастер на машине сборки не
запускается никогда: здесь стоит установленная программа Олега, и тот же
AppId обновил бы её. Установку, обновление поверх и удаление проверяет
приёмка (Т11) на чистой Windows — `docs/dentpilot-2/installer.md` ›
«Обязательная приёмочная проверка».

## Если релиз оказался плохим

1. `Build-Installer.ps1` на исправленном коде, версия **выше** сломанной.
2. Выпустить. Клиники получат её тем же баннером.
3. Сломанный релиз **оставить опубликованным** (правило 3). Если он ещё не
   разошёлся — можно вернуть его в черновик, тогда клиники, не успевшие
   нажать, перестанут его видеть в течение одного цикла опроса.

Обновление идёт мастером: не дошедшая до конца установка откатывается самим
Inno, итог «fail» читает задача-сторож и поднимает прежнюю версию
(`docs/dentpilot-2/updates.md`).

## Песочница: сначала на своём компьютере, потом клиникам

Каналов три. Клиника всегда на `stable` и о двух других не знает.

| канал | что видит | как включается | нужен ключ |
|---|---|---|---|
| `stable` | только опубликованное | по умолчанию | нет |
| `beta` | ещё и **пре-релизы** | `DENTART_CHANNEL=beta` | **нет** |
| `draft` | ещё и **черновики** | наличие токена | да, с записью |

**Рекомендуется `beta`.** В `dental.env` папки данных
(`C:\ProgramData\DentPilot\dental.env`; рядом с exe он лежал до 21.09):

```
DENTART_CHANNEL=beta
```

Пре-релиз публичен — потому ключ и не нужен. Клиника его всё равно не увидит:
на `stable` программа спрашивает единственный эндпоинт `/releases/latest`,
который пре-релизы не отдаёт по устройству GitHub. Это не фильтр, который можно
случайно ослабить, а источник, которому нечего показать лишнего.

### Канал `draft` — только если нужна полная невидимость

⚠️ **Токена с правом чтения НЕДОСТАТОЧНО.** GitHub отдаёт черновики только
обладателю доступа на **запись**; fine-grained токен с `Contents: Read` видит
их ровно как посторонний — то есть никак, молча. Нужен `Contents: Read and
write`, и это ключ, которым можно пушить код и публиковать релизы.

```
DENTART_UPDATE_TOKEN=github_pat_...
```

Такой ключ лежит в папке данных, в файле, который на Windows читают все
учётные записи машины. Ради невидимости черновика это дорогая плата — поэтому
по умолчанию `beta`. Проверить, что канал вообще видит то, что должен:
`python scripts/check_token.py`.

Порядок:

```bash
# 1. собрать
powershell -File Build-Installer.ps1

# 2. тег (создаёт git!) и pre-release скриптом.
#    ⛔ Поимённо, не «--tags» — см. шаг 4 выше
git tag -a v1.11.0 -F <файл-с-описанием>
git push origin v1.11.0
python scripts/release.py prerelease 1.11.0

# 3. своя машина: «Verifică acum» в Setări -> кнопка обновления ->
#    программа перезапускается уже новой. В Setări видна строка
#    «Canal actualizări: beta (pre-lansări)» — перепутать с боевой
#    установкой нельзя.

# 4. поработать в ней. Если плохо — правим и перевыпускаем,
#    клиники ничего не видели.

# 5. хорошо -> опубликовать. Только теперь клиники увидят ту же самую
#    сборку — тот же файл, который уже проверен на своём компьютере.
python scripts/release.py publish 1.11.0
python scripts/release.py check 1.11.0
```

Важно: проверяется **тот самый файл**, который потом получат клиники, а не
похожий. Снятие отметки pre-release (как и Publish у черновика) не пересобирает
ассет — меняется только признак релиза.

## Чего пока нет

- **Репутации у SmartScreen с первого дня.** Подпись есть с 29.09.2026
  (`installer.md` › «Подпись»), но у свежего сертификата SmartScreen ещё
  какое-то время предупреждает при первой установке — уже с именем издателя.
  Обновление этого окна не показывает (мастер скачан не браузером, метки
  Mark-of-the-Web на нём нет).
- **Постепенной раскатки.** Канарейка (`beta`) отделяет свою машину от клиник,
  но дальше релиз доезжает до всех клиник разом: долей «сначала 10%» нет.
- **Понимания, кто на какой версии.** Телеметрии нет; количество скачиваний
  ассета — единственный косвенный признак. Поэтому правило 1 сформулировано
  так, чтобы знать это было **не нужно**.
