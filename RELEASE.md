# Как выпускать версию

Фичи пишутся как обычно. Отличается только момент выпуска — потому что у
DentPilot два потребителя одного и того же кода, и они тянут разные файлы:

| Артефакт | Кто его берёт | Имя |
|---|---|---|
| сама программа | **обновление в один клик** у уже установленных клиник | `DentPilot.exe` — имя фиксировано |
| мастер установки | **новые** клиники: USB, прямая передача | `DentPilot-Setup-X.Y.Z.exe` |
| он же в zip | тот, кто скачивает мастер со страницы релиза | `DentPilot-Setup-X.Y.Z.zip` |

## Три правила, которые нельзя нарушать

**1. В релизе ровно один файл `.exe`, и он называется `DentPilot.exe`.**
Установленная клиника выбирает ассет из списка по имени. Пока в поле остаются
сборки со старым выбором («первый .exe в списке»), второй `.exe` рядом — это
файл, который клиника может скачать вместо программы и затереть им себя.
Поэтому мастер установки уезжает в релиз **архивом**, а не exe. Это правило
постоянное, а не «на один цикл»: клиника, которая пропустила обновление и
включит компьютер через полгода, всё ещё выбирает по-старому.

**2. Имя `DentPilot.exe` — не косметика.** Не переименовывать, не добавлять
версию в имя. Иначе обновление не найдёт файл, и все клиники встанут на
«версия объявлена, файла нет», переспрашивая каждые 5 минут.

**3. Релизы только вперёд.** Не удалять, не снимать с публикации, не
перевешивать метку «latest» на старый релиз. Клиника, которая уже обновилась,
сравнивает свою версию с тегом строго на «больше» — после отката тега она
больше никогда ничего не получит. Плохая сборка чинится **выпуском следующей**.

## Порядок

```bash
# 1. фича закончена и закоммичена (вместе с installer/ и скриптами сборки)
git status --porcelain     # должно быть пусто

# 2. поднять APP_VERSION в bot/app/engine.py — строго три числа X.Y.Z
#    и закоммитить

# 3. собрать и проверить (сборка сама откажется на грязном дереве)
powershell -File Build-Installer.ps1

# 4. только теперь тег — на тот коммит, из которого собрано
git tag v1.11.0 && git push origin main --tags

# 5. черновик релиза -> приложить ДВА файла -> опубликовать
#    dist\DentPilot.exe   и   dist\DentPilot-Setup-1.11.0.zip
#    (черновик именно затем, чтобы клиника не увидела релиз без файла)

# 6. проверить опубликованное глазами клиники
python scripts/check_release.py 1.11.0
```

Шаг 3 идёт **до** тега намеренно: тег — это утверждение о коде, который
действительно собрался и запустился, а не о коде, который мы собирались собрать.

Файлы на шаге 5 перечислять **поимённо**. Никакого `dist/*.exe`: в `dist`
лежит и мастер установки, и он уедет в релиз вторым `.exe` — ровно то, что
запрещает правило 1.

## Что проверяет сборка (и почему)

`Build-Installer.ps1` откажется работать, если:

- **дерево грязное** — иначе тег не воспроизводит бинарник, а недоделанная
  работа из соседнего окна уезжает всем клиникам в один клик;
- **`APP_VERSION` не вида X.Y.Z** — тег `v1.10` даёт `(1, 10)`, что меньше
  `(1, 10, 0)`, и релиз становится невидимым сразу для всех;
- **exe не отвечает на `/health`** — забытый hidden-import даёт молча
  закрывающуюся программу; это единственная проверка, которая его ловит;
- **exe сообщает не ту версию, что в `engine.py`** — значит упаковался старый
  бинарник.

Имя артефакта берётся из того, что **exe сам о себе говорит**, а не из
`engine.py`. Назвать сборку чужой версией больше нельзя — это уже случалось:
`DentPilot-Setup-1.10.0.exe` содержал 1.9.1.

`scripts/check_release.py` проверяет уже опубликованный релиз тем же правилом
сравнения версий, что и программа: draft/pre-release, формат тега, ровно один
`.exe` с правильным именем, состояние и размер ассета.

## Если релиз оказался плохим

1. `Build-Installer.ps1` на исправленном коде, версия **выше** сломанной.
2. Выпустить. Клиники получат её тем же баннером.
3. Сломанный релиз **оставить опубликованным** (правило 3). Если он ещё не
   разошёлся — можно вернуть его в черновик, тогда клиники, не успевшие
   нажать, перестанут его видеть в течение одного цикла опроса.

Обновление, которое не удалось, теперь не равно удалению программы: bat
уводит рабочий exe в `.old`, и при любом сбое возвращает и запускает его.

## Чего пока нет

- **Подписи кода.** Для неподписанного файла SmartScreen считает репутацию по
  хешу файла, то есть **каждая новая версия** начинает с нуля: клиника при
  первой установке всегда видит синее окно «Windows защитила ваш компьютер».
  Обновление в один клик этого окна не показывает (файл скачан не браузером,
  метки Mark-of-the-Web на нём нет).
- **Канареечный выпуск.** Сейчас релиз доезжает до всех клиник сразу.
- **Понимания, кто на какой версии.** Телеметрии нет; количество скачиваний
  ассета — единственный косвенный признак. Поэтому правило 1 сформулировано
  так, чтобы знать это было **не нужно**.
